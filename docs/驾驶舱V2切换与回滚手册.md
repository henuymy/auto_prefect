# 驾驶舱 V2 切换与回滚手册

本手册对应 `驾驶舱V2数据库重构计划.md` 的实施阶段。所有命令默认在项目根目录执行。
任何密码只允许写入被 Git 忽略的 `scripts/dashboard/mysql_env.local.ps1` 或系统密钥管理，
不得粘贴到命令历史、日志、Markdown 和提交记录。

## 1. 切换前硬门槛

必须同时满足：

- 已轮换曾公开过的 root 密码，应用账号不是 root；
- Dashboard MySQL 为 8.0 以上，目标库名为审批后的独立 V2 库（本次为
  `dashboard_v2`），字符集为 `utf8mb4`；
- Prefect Server 使用独立 PostgreSQL，`PREFECT_API_URL` 指向新服务；
- 旧库已完成可恢复备份，并在隔离临时库或临时实例实际恢复成功；
- V2 全量后端测试、真实 MySQL 集成测试、前端类型检查和生产构建通过；
- 新旧 Prefect schedule 均可独立暂停，切换时不会双写。

将 root 轮换、备份恢复演练和审批信息按
`config/dashboard/cutover_approvals.example.json` 写入被 Git 忽略的
`runtime/dashboard_v2_migration/cutover_approvals.json`。文件不得包含密码。

任一阶段都可以运行只读审计：

```powershell
$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v2.local.ps1"
. scripts\dashboard\mysql_env.ps1
python scripts\dashboard\v2_cutover_audit.py --phase preflight
python scripts\dashboard\v2_cutover_audit.py --phase cutover
```

`--require-pk-targets` 只在准备进入 PK 赛期时追加。普通时期允许仅启用 NORMAL/DAY 和
NORMAL/MONTH；没有有效 PK 方案时查询服务会回退到 NORMAL 方案。

审计结果为 `ok=false` 时不得切流；`cutover` 阶段还会要求 `schema_version=2` 和在线 Worker。

## 2. 加载环境与连接预检

```powershell
$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v2.local.ps1"
# 首次部署时复制 example 到上述文件，再填写新库应用账号；不得使用 root。
# V1 回滚配置单独保存在 mysql_env.v1.local.ps1，两个 *.local.ps1 均被 Git 忽略。
. scripts\dashboard\mysql_env.ps1
python -m infrastructure.dashboard_mysql
```

未设置 `DASHBOARD_MYSQL_ENV_FILE` 时仍兼容读取 `mysql_env.local.ps1`。正式迁移必须使用
V1/V2 两个独立本地配置文件，不要在同一个文件中反复手改主机和库名。显式指定的文件
不存在时加载脚本会立即失败，避免静默继承上一个 PowerShell 会话中的旧连接变量。

检查输出中的库名、账号、版本、字符集和时区。账号仅拥有 `dashboard.*` 范围内迁移、
采集、查询和分区维护所需权限，不拥有全局权限和 `GRANT OPTION`。

如果预检发现 `dashboard` 已包含 V1 表或 revision 不是 V2 head，禁止原地执行 V2
迁移。数据库管理员应按 `scripts/dashboard/create_v2_databases.sql.example` 创建：

- `dashboard_v2`：新结构和影子采集；
- `dashboard_v2_ci`：一次性集成测试库，测试会清空其中全部表。

两库仍由同一个 `dashboard_app` 使用，但授权必须分别限制在这两个库内。不得为了省事
给应用账号全局 `CREATE DATABASE` 或 `GRANT OPTION`。

真实 MySQL 集成测试必须先于正式迁移：

```powershell
$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v2.local.ps1"
pwsh -File scripts\dashboard\run_v2_mysql_tests.ps1
```

该脚本从被 Git 忽略的本地环境读取密码，不打印连接串，并拒绝非 test/ci 命名的库。

## 3. 新库迁移与初始化

```powershell
alembic -c alembic_dashboard_v2.ini upgrade head
python scripts\dashboard\initialize_v2_hierarchy.py 已审批基础结构.csv
```

执行上述命令前，`DASHBOARD_MYSQL_DATABASE` 必须明确指向独立 V2 库；如果使用
`dashboard_v2`，初始化命令追加 `--expected-database dashboard_v2`。

基础清单只包含 CITY、BRANCH、GRID。经理和渠道由采集响应建立。初始化可重复执行，
但已存在节点的名称、父级或层级与清单不一致时会拒绝继续。

随后运行指标目录同步。NORMAL 日/月方案是普通时期切换门槛；PK 日/月方案在进入 PK
赛期前导入：

```powershell
python scripts\dashboard\import_v2_target_plan.py 正常日目标.json --expected-database dashboard_v2
python scripts\dashboard\import_v2_target_plan.py 正常月目标.json --expected-database dashboard_v2
python scripts\dashboard\import_v2_target_plan.py PK日目标.json --expected-database dashboard_v2
python scripts\dashboard\import_v2_target_plan.py PK月目标.json --expected-database dashboard_v2
```

旧库配置迁移使用只读导出包，不迁移事实数据：

```powershell
$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v1.local.ps1"
. scripts\dashboard\mysql_env.ps1
# 连接 V1 库时只读导出。
python scripts\dashboard\export_v2_migration_bundle.py --effective-from 2026-07-01

$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v2.local.ps1"
. scripts\dashboard\mysql_env.ps1
# 切到 dashboard_v2 后导入指标设置和公式。
python scripts\dashboard\import_v2_indicator_config.py --expected-database dashboard_v2
```

导出包会生成 NORMAL/DAY 和 NORMAL/MONTH。PK/DAY 与 PK/MONTH 必须由业务方提供，
旧库没有 PK 场景来源时不得伪造或复制 NORMAL 目标冒充 PK 目标。没有启用 PK 方案不影响
普通时期运行，但进入 PK 赛期前必须追加 `--require-pk-targets` 审计。

本次已生成不含目标数值的待填模板：

- `runtime/dashboard_v2_migration/pk_day_target.template.json`：124 个待填键；
- `runtime/dashboard_v2_migration/pk_month_target.template.json`：112 个待填键。

模板只复用已确认的节点和指标键，所有 `target_value` 都是 `null`，生效日期是
`YYYY-MM-DD`，因此不能被导入。业务方必须确认适用键范围、填写数值与生效日期，并另存为
`pk_day_target.json`、`pk_month_target.json`；不得把文件名中的 `.template` 去掉后直接导入。

默认只创建 DRAFT。核对节点数、指标数、目标值数和生效日期后，才允许使用
`--activate-plan-id 方案ID` 激活已核对的 DRAFT。ACTIVE 版本不原地修改，也不要重复导入同一文件来代替激活。

## 4. V2 影子验证

影子阶段不改正式 `schema_version`，每次只允许一个库接收一个批次：

```powershell
$env:DASHBOARD_MYSQL_ENV_FILE = "scripts/dashboard/mysql_env.v2.local.ps1"
. scripts\dashboard\mysql_env.ps1
python scripts\dashboard\run_collection.py --schema-version 2 --mode REALTIME
python scripts\dashboard\run_collection.py --schema-version 2 --mode DAY_ACC
python scripts\dashboard\run_collection.py --schema-version 2 --mode MONTH
```

检查：

- CITY→BRANCH→GRID→CHANNEL_MANAGER→CHANNEL 无断链、空父级、多父级和循环；
- 请求目标约 700，节点规模与上游响应相符，未知层级为 0；
- 经理自身指标每批完整落快照，渠道仅新增、变化和每日检查点落快照；
- current 覆盖启用节点与 STORE 指标的笛卡尔积；
- 日累计、月累计、当前生效场景目标、完成率、排序、自建指标和历史回放正确；
- 单批在 5 分钟内完成，日志无锁等待、死锁和覆盖不完整。

## 5. 分区与 readiness

先把正式配置临时副本的 `schema_version` 设为 2，手工运行一次独立维护 flow，确认未来
30 天日分区已创建。维护使用 `auto_notify_dashboard_partition_maintenance` 锁，采集使用
`auto_notify_dashboard_collection` 锁，两者职责独立。

`/api/live` 只检查进程存活；`/api/health` 必须同时显示：

- Dashboard MySQL 连接正确，库名、非 root 账号、版本、字符集和东八区时区正确；
- Alembic revision 为当前 V2 head；
- 关键表、节点字段、current 唯一约束、snapshot 复合主键和日分区存在；
- Prefect API 可用；
- runtime 可写且磁盘余量达标。

readiness 非 200 时不得恢复 schedule。

## 6. 正式切换

1. 暂停旧 Prefect 的 REALTIME、DAY_ACC、MONTH、INDICATOR_SYNC schedule。
2. 取消暂停前已经生成的 SCHEDULED/PENDING/LATE 重试队列，等待 RUNNING 批次结束；
   仅暂停 deployment 不会自动删除已排队的 flow run，队列未清空前禁止启动 Worker。
3. 记录旧 MySQL、旧 Prefect 配置的恢复位置，不删除旧库和旧代码。
4. 将服务环境的 `DASHBOARD_MYSQL_ENV_FILE` 切到 V2 配置，并重新加载
   `DASHBOARD_MYSQL_*`；同时更新 `PREFECT_API_URL`。
5. 将 `config/dashboard/session.json` 的 `schema_version` 改为 2。
6. 在新 Prefect 发布采集、累计、指标同步和分区维护 deployment；先保持 schedule 暂停。
7. 重启后端，再使用 `scripts/prefect_start.ps1 -Mode worker` 启动 Worker，确认
   `/api/health` 返回 200。脚本会先验证传入的 Prefect API、暂停驾驶舱 deployment、
   取消未开始的排队/重试任务；如果仍有 RUNNING/CANCELLING/PAUSED 批次则拒绝启动，
   不会强制取消在途事务。
8. 手工执行一次 REALTIME，再执行 DAY_ACC 和 MONTH，核对批次和 API。
9. 先恢复分区维护，再恢复采集 schedule；确认旧 Prefect 仍暂停。
10. 连续观察至少 7 天，旧库只读保留。

## 7. 回滚触发条件

出现以下任一情况立即停止 V2 schedule：

- 树结构错误、经理或渠道归属错误；
- current 覆盖不完整、经理指标缺失、历史回放错误；
- 当前生效场景目标、完成率、排序或前端关键链路错误；
- 单批超过 5 分钟或出现持续锁等待、死锁、数据库容量异常；
- V2 readiness 失败或新旧 Prefect 重复调度。

## 8. 回滚步骤

1. 暂停新 Prefect 所有驾驶舱 schedule，等待在途 V2 批次结束。
2. 将 `DASHBOARD_MYSQL_ENV_FILE` 切回 `scripts/dashboard/mysql_env.v1.local.ps1`，恢复旧
   `PREFECT_API_URL` 和 `schema_version=1`，再重新加载环境。
3. 重启后端和 Worker，确认连接旧库且旧 schedule 仍暂停。
4. 按当前业务日期补采旧库，顺序固定为：

```powershell
python scripts\dashboard\run_collection.py --schema-version 1 --mode REALTIME
python scripts\dashboard\run_collection.py --schema-version 1 --mode DAY_ACC
python scripts\dashboard\run_collection.py --schema-version 1 --mode MONTH
```

5. 验证旧库树、current、累计、目标和主要 API 后，恢复旧 schedule。
6. 保留 V2 现场用于分析，不在 V2 库上直接人工改事实数据。

回滚不是只改连接串：旧库在影子和切换期间可能已经落后，三类补采全部成功后才能恢复调度。
