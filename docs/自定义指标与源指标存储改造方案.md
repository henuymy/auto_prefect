# 自定义指标与源指标存储改造方案

## 背景

当前指标库中的指标主要是从外部接口同步来的源指标。新需求是允许用户创建自定义指标：

```text
自定义指标 = 源指标1 * 系数1 + 源指标2 * 系数2 + ...
```

系数默认值为 `1`。

为了控制 `metric_current`、`metric_snapshot`、`metric_acc` 等指标数据表的体积，尤其是高频写入的 `metric_snapshot`，后续希望支持：

```text
源指标可以只参与计算，不一定落库；
自定义指标作为最终展示指标，可以落库；
部分源指标如果业务仍需要，也可以继续落库。
```

因此不能简单地把“源指标”和“自定义指标”混在一个启用状态里处理，需要把“指标类型”和“是否落库展示”拆开。

## 数据模型改造

### indicator 表新增字段

建议给 `indicator` 表增加两个字段：

```text
indicator_type
storage_mode
```

### indicator_type

表示指标的来源或性质：

```text
SOURCE：源指标，来自接口或采集源
CUSTOM：自定义指标，由一个或多个指标按系数计算得到
```

### storage_mode

表示指标是否落库和展示：

```text
STORE：落库并在前端展示
COMPONENT：只作为组件参与计算，不落库、不展示
```

### 字段含义示例

```text
code          name                indicator_type   storage_mode
metric_a      爱家亲情网(V网版)    SOURCE           COMPONENT
metric_b      其他源指标           SOURCE           COMPONENT
custom_aijia  爱家亲情网           CUSTOM           STORE
custom_total  总指标               CUSTOM           STORE
```

## 组合关系表

保留并使用组合关系表：

```text
custom_indicator_component
```

该表表达自定义指标由哪些源指标组成，以及每个源指标的系数。

建议字段：

```text
id
custom_indicator_id
source_indicator_id
coefficient
created_at
updated_at
```

约束建议：

```text
custom_indicator_id -> indicator.id
source_indicator_id -> indicator.id
(custom_indicator_id, source_indicator_id) 唯一
source_indicator_id 建索引
```

示例：

```text
自定义指标 custom_total = metric_a * 1 + metric_b * 2
```

对应关系：

```text
custom_indicator_id   source_indicator_id   coefficient
custom_total          metric_a              1
custom_total          metric_b              2
```

## 核心规则

### 三个关键字段

指标是否参与采集、计算、落库和展示，主要由 `indicator` 表中的三个字段共同决定：

```text
enabled
indicator_type
storage_mode
```

字段职责如下：

```text
enabled：是否启用该指标
indicator_type：指标类型，SOURCE 或 CUSTOM
storage_mode：存储模式，STORE 或 COMPONENT
```

需要特别注意：

```text
indicator_type 不直接决定是否落库。
真正决定是否落库的是 enabled + storage_mode。
```

也就是说：

```text
SOURCE / STORE      会落库
CUSTOM / STORE      会落库
SOURCE / COMPONENT  不落库
CUSTOM / COMPONENT  不落库
```

### 请求哪些指标

采集阶段需要请求的源指标包括：

```text
1. enabled=1 且 indicator_type=SOURCE 且 storage_mode=STORE 的源指标
2. enabled=1 且 indicator_type=CUSTOM 且 storage_mode=STORE 的自定义指标引用到的源指标
```

也就是说：

```text
源指标只要自己要落库，或者被某个要落库的自定义指标使用，就需要请求。
```

请求阶段只请求源指标，因为自定义指标不是从外部接口直接返回，而是由源指标计算得到。

当前规则可以理解为：

```text
请求源指标 =
  SOURCE / STORE 指标
  +
  CUSTOM / STORE 自定义指标引用到的 SOURCE 指标
```

### 计算哪些指标

采集拿到源指标值后，在内存中计算自定义指标：

```text
custom_value = sum(source_value * coefficient)
```

如果某个源指标没有值，则跳过该源指标。只有所有源指标都没有值时，自定义指标返回空值。

### 落库哪些指标

只落库：

```text
enabled=1 且 storage_mode=STORE 的指标
```

完整判断条件是：

```text
indicator.enabled = 1
AND indicator.storage_mode = 'STORE'
```

`indicator_type` 不参与最终落库判断。

包括：

```text
SOURCE / STORE
CUSTOM / STORE
```

不落库：

```text
SOURCE / COMPONENT
CUSTOM / COMPONENT
```

需要写入的表包括：

```text
metric_current
metric_snapshot
metric_acc
```

因此不同组合的行为如下：

```text
indicator_type   storage_mode   行为
SOURCE           STORE          请求、落库、展示
SOURCE           COMPONENT      只在被公式引用时请求；不落库、不展示
CUSTOM           STORE          计算、落库、展示
CUSTOM           COMPONENT      通常不使用；不落库、不展示
```

### 前端展示哪些指标

查询接口只返回：

```text
enabled=1 且 storage_mode=STORE
```

因此前端只展示需要落库展示的指标，不展示纯组件指标。

完整判断条件是：

```text
indicator.enabled = 1
AND indicator.storage_mode = 'STORE'
```

同样，`indicator_type` 不直接决定是否展示。

## 当前实现 Review

当前代码实现与上述规则一致：

```text
1. 查询接口使用 enabled=1 AND storage_mode=STORE 选择前端可见指标
2. 写入 metric_current / metric_snapshot / metric_acc 前会校验 enabled=1 AND storage_mode=STORE
3. 采集计划会请求 SOURCE / STORE 指标
4. 采集计划也会请求 CUSTOM / STORE 自定义指标引用到的源指标
5. 自定义指标保存时，自定义指标会被设置为 CUSTOM / STORE
6. 每个源指标是否改为 STORE 或 COMPONENT，由 source_storage_mode 控制
```

需要注意的边界：

```text
1. 迁移后老指标默认是 SOURCE / STORE，所以不会突然停止落库
2. 想让某个源指标只参与计算，必须在指标管理中把它设为 COMPONENT
3. 如果源指标同时要自己落库，又要参与自定义指标，设置为 SOURCE / STORE 即可
4. 如果源指标只用于自定义指标，不希望进入 metric_snapshot，设置为 SOURCE / COMPONENT
```

结论：

```text
当前落库判断没有和 indicator_type 冲突。
indicator_type 负责说明指标来源，storage_mode 负责控制是否落库/展示。
```

## 典型场景

### 场景 1：自定义指标等于单个源指标

例如：

```text
爱家亲情网 = 爱家亲情网(V网版)
```

配置：

```text
code             indicator_type   storage_mode
sgs_ajvwdz       SOURCE           COMPONENT
custom_aijia     CUSTOM           STORE
```

公式：

```text
custom_aijia = sgs_ajvwdz * 1
```

采集时：

```text
请求 sgs_ajvwdz
计算 custom_aijia
只落库 custom_aijia
```

### 场景 2：自定义指标包含多个源指标

例如：

```text
总指标 = A + B * 2
```

配置：

```text
code          indicator_type   storage_mode
A             SOURCE           COMPONENT
B             SOURCE           COMPONENT
custom_total  CUSTOM           STORE
```

公式：

```text
custom_total = A * 1 + B * 2
```

采集时：

```text
请求 A、B
计算 custom_total
只落库 custom_total
```

### 场景 3：源指标既参与自定义指标，也要自己落库

例如：

```text
C = A + B
```

业务希望：

```text
A 自己也落库展示
B 只参与计算
C 自定义指标落库展示
```

配置：

```text
code   indicator_type   storage_mode
A      SOURCE           STORE
B      SOURCE           COMPONENT
C      CUSTOM           STORE
```

公式：

```text
C = A * 1 + B * 1
```

采集时：

```text
请求 A、B
计算 C
落库 A、C
不落库 B
```

前端展示：

```text
A、C
```

## 对历史数据的影响

如果只存自定义指标，不存源指标历史值，会有以下影响：

```text
1. 系数修改后，历史值不会自动按新系数重算
2. 新增自定义指标后，历史值无法回填
3. 无法查看未落库源指标的历史明细
```

原因是历史库中没有源指标值，就无法重新按新公式计算历史结果。

例如：

```text
C = A + B * 2
```

历史只存了：

```text
C = 43
```

但没有存：

```text
A = ?
B = ?
```

以后新增：

```text
D = A * 3 + B
```

则历史的 `D` 无法补算。

如果业务主要看当前批次、今日盯控、最近变化，这个影响较小；如果后续要做长期复盘、同比环比、历史口径重算，则需要保留更多源指标历史。

## 推荐上线策略

### 第一步：新增字段和关系表

新增：

```text
indicator.indicator_type
indicator.storage_mode
custom_indicator_component
```

当前已有源指标根据实际需求设置：

```text
需要自己展示/落库的源指标：SOURCE / STORE
只参与计算的源指标：SOURCE / COMPONENT
```

### 第二步：调整自定义指标保存逻辑

保存自定义指标时：

```text
自定义指标：indicator_type=CUSTOM, storage_mode=STORE
源指标：保持 SOURCE；storage_mode 是否改为 COMPONENT 由用户选择
```

不要默认把所有被引用的源指标都改成 `COMPONENT`，因为有些源指标可能既参与公式，也需要自己落库。

### 第三步：调整采集逻辑

采集流程改为：

```text
1. 找出需要请求的源指标
2. 请求接口得到源指标值
3. 在内存中计算自定义指标值
4. 只写入 storage_mode=STORE 的指标
```

### 第四步：调整查询逻辑

查询接口只返回：

```text
enabled=1 AND storage_mode=STORE
```

对已经落库的自定义指标，查询时直接读取 `metric_*` 表，不再动态计算。

### 第五步：旧数据处理

不建议上线时直接删除旧数据。

建议：

```text
1. 先停止继续写 COMPONENT 指标
2. 观察一段时间
3. 确认无问题后，再单独写清理脚本删除历史 metric_snapshot 中不需要的源指标数据
```

## 测试重点

需要覆盖以下场景：

```text
1. SOURCE / COMPONENT 指标会被请求，但不落库、不展示
2. SOURCE / STORE 指标会被请求、落库、展示
3. CUSTOM / STORE 指标会被计算、落库、展示
4. 自定义指标等于单个源指标时，结果正确
5. 自定义指标包含多个源指标和系数时，结果正确
6. 源指标既参与公式又自己落库时，源指标和自定义指标都能落库
7. 查询接口只返回 storage_mode=STORE
8. metric_snapshot 不再写入 COMPONENT 指标
```

## 最终结论

推荐方案是：

```text
indicator_type 负责区分 SOURCE / CUSTOM
storage_mode 负责控制 STORE / COMPONENT
custom_indicator_component 负责表达公式关系
metric_* 只写 storage_mode=STORE 的指标
```

这样既能支持“只存自定义指标”，也能支持“部分源指标仍然落库”，并且可以有效控制 `metric_snapshot` 的数据增长。
