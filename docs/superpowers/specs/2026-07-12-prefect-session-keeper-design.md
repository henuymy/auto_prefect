# Prefect Session Keeper 设计

## 目标

在单台 Windows 机器上，通过 Prefect 定时维护自动通报系统使用的共享登录会话。会话管理应提前发现认证失效、自动恢复，并允许业务 Flow 在执行期间即时触发恢复，同时避免并发登录、登录风暴和敏感信息泄露。

## 范围

- Session Keeper 代码属于当前项目。
- 使用现有 `services.session_manager`、登录流程、Cookie 文件、浏览器配置和全局登录锁。
- 使用常驻后台 Edge 会话。
- 使用 Prefect 负责调度、运行记录、失败状态和重试编排。
- 实验 runner 仅用于会话寿命实验，不属于生产 Session Keeper，也不在本方案中修改。

## 总体架构

Session Keeper 采用短时 Prefect Flow，而不是永不结束的守护 Flow。Deployment 使用 `*/15 * * * *`，时区为 `Asia/Shanghai`，在每小时的 `00`、`15`、`30`、`45` 分运行。

建议组件边界：

- `services/session_manager.py`：Cookie 校验、阶段探活、故障分类、锁内复检和会话刷新。
- `tasks/session_tasks.py`：将会话准备和刷新包装为 Prefect Task。
- `flows/session_keeper_flow.py`：执行一次完整的会话健康检查与必要恢复。
- `prefect.yaml`：声明 Session Keeper Deployment 和固定时间调度。
- 企业微信通知能力：发送失败告警与恢复通知。

业务 Flow 与 Keeper Flow 使用相同的 Session Manager、Cookie 文件、Edge 用户目录和全局登录锁。Prefect 负责调用和观测，不直接实现浏览器登录细节。

## Keeper Flow

每次 Keeper Flow 执行以下步骤：

1. 读取共享 Cookie 和会话状态。
2. 对 `report_analysis`、`smart_ops`、`city_ops` 执行阶段探活。
3. 全部通过时记录健康状态并结束。
4. 出现明确认证失败时获取全局登录锁。
5. 在锁内再次探活，避免其他 Flow 已完成刷新后重复登录。
6. 仍为认证失败时立即执行第一次登录。
7. 第一次登录失败后等待 60 秒，仅重试一次。
8. 任意一次登录成功后，重新探活全部三个阶段；全部通过后才原子更新共享会话并标记恢复。
9. 累计两次登录失败后停止本次 Keeper Flow，标记失败并发送告警。

Keeper Flow 不采用实验中的 3 分钟复探和连续失败阈值。生产策略以快速恢复为目标。

## 故障分类

### 认证失败

以下情况视为认证失败，立即进入锁内刷新流程：

- HTTP `302`、`401`、`403`。
- 必需 Cookie、Token 或 Storage 字段缺失。
- 接口返回明确的未登录状态或业务认证失败码。
- 探活响应结构有效，但关键结果与配置的成功值不一致。

任一必需阶段出现认证失败，刷新整套共享会话。三个阶段来自同一次 SSO 登录，Cookie 与 Storage 必须作为同一快照更新。

### 基础设施或网络失败

以下情况不触发登录：

- DNS、连接超时或连接拒绝。
- VPN 或内部网络不可用。
- TLS、代理或目标服务器不可达。
- Prefect Worker 或本机资源异常。

这类错误由 Prefect 标记、重试并告警。重新登录不能修复网络故障，因此必须避免反复启动 Edge。

## 业务 Flow 集成

每个业务 Flow 在开始时调用 `prepare_session_task()`，健康会话直接复用。

业务请求执行期间如果出现明确认证失败：

1. 业务 Flow 可以立即请求同一套会话刷新逻辑，不必等待下一次 Keeper 调度。
2. 刷新必须经过全局登录锁和锁内复检。
3. 每个业务 Flow 最多主动刷新一次。
4. 刷新成功后仅重试失败的业务步骤一次，不重跑已完成步骤。
5. 刷新后仍认证失败时，业务 Flow 失败并告警，不进入无限循环。
6. 网络错误不消耗业务 Flow 的主动刷新额度。

## 并发控制

- 同一时间只允许一个登录操作。
- Keeper Flow、通报 Flow、驾驶舱 Flow 和手工触发共用同一把跨进程文件锁。
- 获取锁后必须重新读取 Cookie 并再次探活。
- 等待者发现会话已恢复时直接复用，不重复登录。
- Cookie、Storage 和会话元数据使用临时文件加原子替换方式发布，消费者不能读取半写入状态。

## 重试和停止条件

- 认证失败后立即进行第一次登录。
- 第一次登录失败后等待 60 秒。
- 仅执行一次重试，累计最多两次登录尝试。
- 第二次仍失败后，本次 Flow 停止并进入失败状态。
- 下一次自动恢复机会来自下一次 15 分钟 Keeper 调度，或新的业务 Flow 即时刷新请求。
- 不允许在单次 Flow 中无限重试。

## 告警

累计两次登录失败后，通过现有企业微信机器人发送告警，同时保留 Prefect 失败状态和完整日志。

告警内容包括：

- Windows 主机标识。
- 触发来源：Keeper Flow 或具体业务 Flow。
- 失败阶段和故障分类。
- 两次登录尝试的脱敏错误摘要。
- Prefect Flow Run ID 和可查询的运行信息。
- 下次 Keeper 调度时间。

告警不得包含用户名、密码、Cookie、Token、Storage 原值或企业微信 Webhook。相同故障周期只发送一次告警；会话恢复后发送一次恢复通知，并清除告警抑制状态。

## 启动和运行

统一 Windows 启动脚本负责启动 Prefect Server、同步 Deployment、启动 Worker 和管理端。Session Keeper 不需要额外的长期 Python 守护进程，由 Prefect Cron 定时执行。

系统首次启动时应主动触发一次 Keeper Flow，避免等待下一个 15 分钟整刻。Prefect Worker 重启后，业务 Flow 的启动前检查和下一次 Keeper 调度均可恢复会话。

## 可观测状态

每次 Keeper Flow 至少记录：

- 探活时间和各阶段结果。
- 故障分类。
- 是否复用、等待或刷新会话。
- 登录锁等待时间。
- 登录尝试次数和耗时。
- 登录后验证结果。
- Cookie 快照更新时间，但不记录认证值。
- 告警发送或抑制状态。

## 验收标准

- Keeper Deployment 严格在每 15 分钟整刻运行。
- 健康会话不会触发登录。
- 任一阶段明确认证失败会立即刷新整套会话。
- 网络故障不会触发登录。
- 并发触发时只发生一次登录，其余调用复用结果。
- 第一次登录失败后等待 60 秒且仅重试一次。
- 两次登录失败后 Flow 失败并发送一次企业微信告警。
- 恢复后发送一次恢复通知。
- 业务 Flow 能即时刷新并仅重试失败步骤一次。
- 日志、状态文件和告警中不出现认证秘密。

## 非目标

- 不修改或替代会话寿命实验 runner。
- 不引入独立 HTTP Session Keeper 服务。
- 不支持多台机器共享同一浏览器实例。
- 不在本方案中拆分 Linux 控制节点和 Windows Excel Worker。
