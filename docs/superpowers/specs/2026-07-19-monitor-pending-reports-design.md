# 通报待执行队列筛选设计

## 目标

运行监控中心的“待执行”入口和抽屉只展示自动通报任务的 Scheduled 计划实例。会话维护与驾驶舱采集任务不在此队列中显示。

## 决策

前端在 `MonitorCenter` 接收到 `PendingQueue` 后派生通报队列。一个实例仅在其 `targetId` 以 `report-` 开头时保留。该前缀是稳定的业务标识；不得依赖可展示、可本地化的 `target` 文案。

派生队列的 `items` 为过滤结果，`total` 必须为该结果的长度，范围标签为“通报当前 Scheduled”。待执行按钮和 `PendingQueueDrawer` 均使用这一份派生队列，因此计数、抽屉摘要和时间线始终一致。

## 数据流与边界

`MonitorCenter` 保持接收服务提供的完整 `pendingQueue`，以便不改变 API 契约或实时流协议。它在渲染时通过 memoization 派生通报队列；初次加载与实时流更新都会重新计算该值。

运行历史、筛选条件、状态汇总、详情抽屉和后端 API 均不在本次范围内。加载中的空队列状态保持现有行为。

## 验收标准

- 现有模拟队列中的 48 条计划被筛选为 24 条通报计划。
- 待执行按钮显示 24，aria 标签与可见计数一致。
- 打开的待执行抽屉显示 24 条、范围标签为“通报当前 Scheduled”，且不显示会话维护或驾驶舱采集任务。
- 实时队列更新继续应用相同的筛选规则。

## 测试

更新监控中心组件测试，断言通报待执行计数为 24；打开队列后断言通报任务存在，非通报任务不存在。执行目标测试、全量前端测试、TypeScript 构建，并通过浏览器检查监控页的按钮和抽屉。
