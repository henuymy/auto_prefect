# 驾驶舱历史时间语义完善设计

## 目标

在不改变 V1 兼容行为的前提下，让接口调用方和页面用户明确理解：历史选择器中的时间是采集批次的开始时间，即“采集档位”，不是数据实际完成时间。变化值仍按理论基线时间前后 3 分钟选择最近快照。

## 不在本次范围内

- 不修改历史批次选择规则；历史批次继续按 `started_at` 归属采集档位。
- 不修改历史数据截止点；主历史值继续读取所选批次完成时间之前的快照。
- 不修改变化基线的正负 3 分钟容差以及稀疏快照向前取值规则。
- 不把快照存在性子查询未关联具体批次认定为历史时间错误，也不在本次修改其行为。

## 接口设计

历史查询响应的 `history_meta` 保留现有字段，并新增：

```json
{
  "batch_started_at": "2026-06-30T10:05:10.000",
  "batch_finished_at": "2026-06-30T10:08:30.000",
  "duration_seconds": 200,
  "fallback_seconds": 50,
  "is_fallback": true,
  "time_basis": "BATCH_STARTED_AT",
  "change_tolerance_minutes": 3
}
```

- `time_basis` 固定为 `BATCH_STARTED_AT`，表明历史日期和时间选项来自批次开始时间。
- `change_tolerance_minutes` 返回当前变化基线容差，值来自后端既有 `CHANGE_WINDOW_TOLERANCE_MINUTES` 常量，避免接口说明与计算规则漂移。
- 新字段只做语义声明，不参与批次或快照计算。

## 页面设计

- 将历史选择区的“历史时刻”改为“采集档位（批次开始时间）”。
- 历史查询结果将“实际批次”改为“匹配批次开始时间”。
- 已有“完成 HH:mm:ss”信息继续显示，并改成明确的“批次完成时间 HH:mm:ss”。
- 在历史选择区提供简短说明：变化值会在理论基线时间前后 3 分钟内选择最近快照；没有附近快照时，稀疏渠道数据按既有规则向前取最近值。
- 实时模式中的“当前批次”显示完成时间，不与历史采集档位混用。

## 快照存在性子查询评估

V1 和 V2 的历史批次选择均包含一个快照可用性保护，但该子查询没有用 `collection_run_id` 关联候选批次。它的当前作用是避免在保留窗口之外选择完全没有可用快照的时间段，而不是证明候选批次自身写入过快照。

本次保留该行为，原因是 V2 快照对渠道采用稀疏存储，历史值允许从候选批次之前向前取最近值；直接强制候选批次必须拥有每个目标节点或指标的快照会改变 V1 兼容语义。后续若要收紧，应先定义“批次至少有一条快照”还是“查询范围内每个指标均有可恢复快照”，并通过生产数据验证后单独实施。

## 测试设计

- 后端单元测试断言 `history_meta.time_basis == "BATCH_STARTED_AT"`。
- 后端单元测试断言 `history_meta.change_tolerance_minutes == 3`，且来源于共享常量。
- 保留并运行现有“批次完成较晚但按开始时间归档”和“正负 3 分钟最近快照”测试，证明计算语义未改变。
- 前端测试断言历史选择器显示“采集档位（批次开始时间）”、匹配批次开始时间和批次完成时间。
- TypeScript 类型补充两个只读语义字段，构建应无类型错误。

## 验收标准

1. 选择历史时间时，页面不再把采集档位描述成数据完成时刻。
2. API 明确返回批次时间基准和变化快照容差。
3. V1 兼容的批次选择、快照截止点和正负 3 分钟规则保持不变。
4. 后端测试、前端测试、前端构建和静态检查全部通过。
