# 自动化通报系统模块设计文档

## 1. 文档目的
本文档用于定义自动化通报系统的模块划分、职责边界、调用顺序、输入输出、状态流转与扩展方向，作为后续编码实现的设计依据。

---

## 2. 系统定位
自动化通报系统用于完成以下闭环流程：

**读取配置 → 调度任务 → 登录系统 → 下载报表 → 数据比对 → 生成临时副本 → 写入模板 → 联动计算 → 截图取词 → 发送通报 → 更新正式模板 → 记录日志与重试**

系统采用以下原则：

- 以 **JSON** 作为任务配置载体
- 以 **正式模板 + 临时副本** 作为 Excel 处理方式
- 以 **先比对、后写入** 作为数据处理原则
- 以 **发送成功后再更新正式模板** 作为基线提交原则
- 以 **失败后按间隔重试** 作为异常恢复机制

---

## 3. 总体架构

## 3.1 架构说明
系统采用：

- 一个主控调度入口
- 多个职责明确的业务模块
- 统一的状态与日志管理
- 后续按需插件化的扩展能力

---

## 3.2 模块划分
建议分为以下核心模块：

1. `config_manager`：配置读取与校验
2. `scheduler`：调度与重试管理
3. `login_handler`：登录与会话管理
4. `report_handler`：报表下载与初步解析
5. `compare_handler`：数据标准化与比对
6. `template_handler`：模板复制、写入、联动、截图、取词
7. `notify_handler`：消息发送
8. `commit_handler`：正式模板更新
9. `state_manager`：状态、日志、重试记录
10. `app`：主控流程编排

## 5. 核心数据对象设计

## 5.1 TaskConfig
表示一个通报任务的静态配置。

建议字段：

- `task_name`：任务名称
- `enabled`：是否启用
- `login_key`：登录配置标识
- `report_request`：报表下载参数
- `template_path`：正式模板路径
- `temp_dir`：临时目录
- `raw_sheet_name`：原始数据页名称
- `notify_sheet_name`：通报展示页名称
- `notify_text_sheet_name`：通报词页名称
- `screenshot_ranges`：截图区域列表
- `notify_text_cells`：通报词单元格列表
- `wechat_groups`：目标群列表
- `schedule_times`：每日执行时间点列表
- `retry_interval_minutes`：失败重试间隔
- `max_retry_count`：最大重试次数

---

## 5.2 TaskInstance
表示某个任务在某一天某个时间点的一次执行实例。

建议字段：

- `instance_id`
- `task_name`
- `biz_date`
- `schedule_time`
- `retry_index`
- `status`
- `trigger_time`
- `next_retry_time`
- `error_message`

推荐实例标识格式：

```text
{task_name}_{biz_date}_{schedule_time}_{retry_index}
```

示例：

```text
日通报A_2026-04-18_09:00_0
```

---

## 5.3 CompareResult
表示数据比对结果。

建议字段：

- `result`：`same / changed / invalid`
- `diff_summary`
- `new_row_count`
- `old_row_count`

---

## 5.4 NotifyPayload
表示待发送的通报内容。

建议字段：

- `image_paths`
- `text_content`
- `group_targets`

---

## 5.5 ExecutionRecord
表示一次执行记录。

建议字段：

- `instance_id`
- `step_name`
- `status`
- `start_time`
- `end_time`
- `retry_index`
- `message`

## 6. 模块设计

## 6.1 config_manager 模块

### 职责
负责读取和校验 JSON 配置文件，输出标准化任务配置对象。

### 输入
- JSON 配置文件路径

### 输出
- `list[TaskConfig]`

### 主要功能
- 读取 JSON
- 校验必填字段
- 校验时间格式
- 校验路径和参数格式
- 过滤禁用任务

### 主要接口建议
```python
load_config(config_path: str) -> list
validate_task_config(task: dict) -> None
```

### 异常
- 配置文件不存在
- JSON 格式错误
- 字段缺失
- 时间格式非法
- 模板路径缺失

---

## 6.2 scheduler 模块

### 职责
负责判断当前应执行哪些任务实例，并计算失败任务的重试计划。

### 输入
- 当前时间
- 全部任务配置
- 任务状态记录

### 输出
- `list[TaskInstance]`

### 主要功能
- 判断是否命中每日执行时间点
- 判断失败任务是否达到重试时间
- 避免同一实例重复触发
- 计算下一次重试时间

### 主要接口建议
```python
get_due_task_instances(now, task_configs, state_store) -> list
build_task_instance(task_config, biz_date, schedule_time, retry_index) -> object
calculate_next_retry_time(failed_time, retry_interval_minutes, retry_index)
```

### 异常
- 时间解析错误
- 状态文件异常
- 重试状态不一致

---

## 6.3 login_handler 模块

### 职责
负责业务系统登录与会话管理。

### 输入
- `login_key`
- 登录参数

### 输出
- `session / cookie / token`

### 主要功能
- 登录系统
- 校验会话有效性
- 会话失效时重新登录

### 主要接口建议
```python
login(login_key: str) -> object
check_session(session_obj) -> bool
refresh_session(login_key: str) -> object
```

### 异常
- 登录失败
- 验证码 / 单点登录异常
- 会话超时

---

## 6.4 report_handler 模块

### 职责
负责报表下载、文件保存与初步解析。

### 输入
- 会话对象
- 报表请求参数

### 输出
- 原始下载文件路径
- 标准化前的数据对象

### 主要功能
- 发起下载请求
- 保存原始文件
- 解析 Excel / CSV / JSON
- 返回统一格式的数据框架

### 主要接口建议
```python
download_report(session_obj, report_request) -> str
parse_report(file_path: str)
fetch_and_parse(session_obj, report_request)
```

### 异常
- 请求失败
- 文件为空
- 文件格式不支持
- 数据解析失败

---

## 6.5 compare_handler 模块

### 职责
负责读取正式模板原始数据页，并对新旧数据进行标准化和比对。

### 输入
- 新下载数据
- 正式模板路径
- 原始数据页名称

### 输出
- `CompareResult`

### 主要功能
- 读取正式模板原始数据页
- 清洗空行空列
- 统一字段和类型
- 比对新旧数据
- 输出是否变化

### 主要接口建议
```python
load_old_data_from_template(template_path: str, raw_sheet_name: str)
normalize_dataframe(df)
compare_data(new_df, old_df) -> dict
```

### 异常
- 模板读取失败
- 原始数据页不存在
- 数据结构异常
- 列不匹配

### 说明
该模块是流程分叉点：

- `same`：结束本次实例，不重试
- `changed`：继续后续流程
- `invalid`：记为失败，可重试

---

## 6.6 template_handler 模块

### 职责
负责临时副本生成、原始数据写入、模板联动、截图与通报词提取。

### 输入
- 正式模板路径
- 临时目录
- 新数据
- 截图配置
- 通报词配置

### 输出
- 临时副本路径
- 图片路径列表
- 通报文字

### 主要功能
- 复制正式模板为临时副本
- 写入原始数据页
- 触发模板联动结果
- 截取指定区域
- 提取通报词

### 主要接口建议
```python
create_temp_copy(template_path: str, temp_dir: str, instance_id: str) -> str
write_raw_data(temp_template_path: str, raw_sheet_name: str, new_df) -> None
render_template(temp_template_path: str) -> None
capture_screenshots(temp_template_path: str, sheet_name: str, ranges: list) -> list
extract_notify_text(temp_template_path: str, sheet_name: str, cells: list) -> str
build_notify_payload(...) -> dict
```

### 异常
- 模板复制失败
- 写入失败
- Excel 公式异常
- 截图失败
- 通报词为空

### 说明
该模块内部逻辑较多，但当前阶段建议先合并实现，等后续复杂度提升后再进一步拆分。

---

## 6.7 notify_handler 模块

### 职责
负责将生成的图片和文字发送到目标微信群。

### 输入
- `NotifyPayload`

### 输出
- 发送结果对象

### 主要功能
- 发送图片
- 发送文字
- 返回成功或失败状态
- 返回失败原因

### 主要接口建议
```python
send_images(group_targets: list, image_paths: list) -> bool
send_text(group_targets: list, text_content: str) -> bool
send_notify(payload: dict) -> dict
```

### 异常
- 发送接口失败
- 群目标不可达
- 图片发送失败
- 文本发送失败

### 发送顺序
必须遵循：

1. 先发送图片
2. 再发送文字

---

## 6.8 commit_handler 模块

### 职责
负责在发送成功后更新正式模板，使本次数据成为新的基线。

### 输入
- 正式模板路径
- 临时副本路径

### 输出
- 提交结果

### 主要功能
- 安全替换正式模板
- 防止更新中断导致模板损坏
- 确保模板完整性

### 主要接口建议
```python
commit_template(temp_template_path: str, formal_template_path: str) -> bool
safe_replace_file(src: str, dst: str) -> bool
```

### 异常
- 文件占用
- 权限不足
- 覆盖失败
- 提交中断

### 关键规则
只有在发送成功后，主控流程才允许调用该模块。

---

## 6.9 state_manager 模块

### 职责
负责状态流转、执行日志、失败日志和重试记录。

### 输入
- 任务实例
- 步骤名
- 状态
- 错误信息

### 输出
- 日志文件 / 状态记录

### 主要功能
- 记录每一步执行状态
- 记录失败原因
- 记录重试次数
- 记录最终成功或最终失败
- 支持调度器查询当前实例状态

### 主要接口建议
```python
mark_instance_running(instance_id: str) -> None
mark_instance_success(instance_id: str) -> None
mark_instance_failed(instance_id: str, error_message: str) -> None
mark_instance_retry_waiting(instance_id: str, next_retry_time) -> None
append_step_log(record: dict) -> None
get_instance_status(instance_id: str)
```

### 异常
- 日志文件损坏
- 状态文件冲突
- 重试记录不一致

---

## 6.10 app 模块

### 职责
作为主控入口，串联所有模块，执行完整流程。

### 输入
- 配置文件路径
- 当前时间

### 输出
- 无直接业务输出，负责驱动整个系统运行

### 主要功能
- 加载配置
- 获取待执行实例
- 按顺序调用各模块
- 做流程分支和异常控制

### 伪代码示例
```python
for instance in scheduler.get_due_task_instances(...):
    try:
        state.mark_instance_running(instance.id)

        session = login_handler.login(instance.task.login_key)
        new_data = report_handler.fetch_and_parse(session, instance.task.report_request)

        compare_result = compare_handler.compare_data(
            new_data,
            instance.task.template_path,
            instance.task.raw_sheet_name
        )

        if compare_result["result"] == "same":
            state.mark_instance_success(instance.id)
            continue

        if compare_result["result"] == "invalid":
            raise Exception("数据异常，无法比较")

        temp_path = template_handler.create_temp_copy(...)
        template_handler.write_raw_data(temp_path, ...)
        template_handler.render_template(temp_path)

        payload = template_handler.build_notify_payload(...)
        send_result = notify_handler.send_notify(payload)

        if not send_result["success"]:
            raise Exception(send_result["message"])

        commit_handler.commit_template(temp_path, instance.task.template_path)
        state.mark_instance_success(instance.id)

    except Exception as e:
        state.mark_instance_failed(instance.id, str(e))
        scheduler.schedule_retry_if_needed(instance, str(e))
```

```text

→ 登录
→ 下载报表
→ 读取正式模板旧数据
→ 新旧数据比对
→ 一致则结束
→ 生成临时副本
→ 写入新数据
→ 模板联动
→ 截图/提取通报词
→ 发送图片
→ 发送文字

```

## 8. 状态流转设计

建议状态如下：

- `PENDING`：待执行
- `RUNNING`：执行中
- `NO_CHANGE`：数据无变化
- `RETRY_WAITING`：等待重试
- `SUCCESS`：执行成功
- `COMMITTED`：正式模板提交成功
- `FAILED`：本次执行失败
- `FINAL_FAILED`：达到最大重试次数后仍失败

状态流转示意：

```text
PENDING
→ RUNNING
→ NO_CHANGE
或
→ SUCCESS
→ COMMITTED
或
→ FAILED
→ RETRY_WAITING
→ RUNNING
→ ...
→ FINAL_FAILED
```

## 9. 重试机制设计

## 9.1 可重试场景
以下情况建议进入重试：

- 登录失败
- 下载失败
- 数据解析失败
- 模板复制失败
- 模板写入失败
- 截图失败
- 通报词提取失败
- 消息发送失败
- 正式模板更新失败

---

## 9.2 不重试场景
以下情况不属于失败，不应重试：

- 数据无变化
- 当前未到执行时间
- 任务被禁用

---

## 9.3 重试规则
每个任务时间点实例都拥有独立重试计数：

- 首次执行为 `retry_index = 0`
- 失败后按 `retry_interval_minutes` 推算下一次重试时间
- 达到 `max_retry_count` 后记为 `FINAL_FAILED`

## 11. 后续插件化建议

当前阶段先以模块化实现为主，后续优先考虑将以下能力插件化：

### 11.1 登录插件
适用于不同系统采用不同登录方式的场景。

### 11.2 报表下载插件
适用于不同系统下载方式差异较大的场景。

### 11.3 消息发送插件
适用于后续扩展到：

- 微信群
- 企业微信
- 钉钉
- 邮件
- 飞书

不建议过早插件化的模块：

- 数据比对
- 模板处理
- 正式模板提交
- 状态管理

## 12. 第一阶段落地建议

1. JSON 配置读取
2. 单任务时间点调度
3. 登录与下载

## 13. 设计结论
本系统建议采用：

- **设计上：按多个 Skill 划分职责**
- **实现上：按多个 Python 模块组织代码**
- **运行上：由一个主控入口统一编排**
- **扩展上：后续按需将登录、下载、发送逐步插件化**

这样既能保证当前实现可控，也能为后续复杂化预留扩展空间。
