# 数据驾驶舱设计说明

## 1. 项目背景

数据驾驶舱是“自动通报”项目的扩展功能，用于定时采集地市平台指标数据，将数据保存到云服务器 MySQL，并通过 Web 页面展示实时指标、排名、趋势和变化情况。

数据驾驶舱与自动通报最终合并为同一个项目，但两者保持独立的业务处理流程和数据库。

## 2. 核心目标

第一阶段目标是跑通以下链路：

```text
地市平台
  -> 自动登录及会话复用
  -> 每 5 分钟采集数据
  -> 数据标准化
  -> 批量写入云服务器 MySQL
  -> FastAPI 查询接口
  -> React 数据驾驶舱
```

首期只处理以下层级：

```text
分公司 BRANCH
  -> 网格 GRID
  -> 渠道/营业厅 CHANNEL
```

暂时不处理人员 `STAFF` 层级。

## 3. 与自动通报的关系

### 3.1 复用的公共能力

数据驾驶舱复用自动通报已有的：

- 自动登录和验证码处理
- 浏览器会话维护
- 地市平台 `uapToken` 获取
- Session 探活和失效重登
- 地市平台 HTTP 请求基础能力
- Prefect 定时调度
- 运行日志和异常处理

### 3.2 保持独立的能力

自动通报继续负责：

```text
地市平台 -> Excel -> 数据对比 -> 企业微信通报
```

数据驾驶舱单独负责：

```text
地市平台 -> 数据标准化 -> MySQL -> 查询 API -> 可视化页面
```

不要让驾驶舱采集逻辑依赖 Excel 文件，也不要让自动通报改用驾驶舱 MySQL。

## 4. 数据库原则

### 4.1 数据库相互独立

- 自动通报继续使用原数据库和原 Prefect 配置。
- 数据驾驶舱使用云服务器上的独立 MySQL 数据库。
- 不迁移自动通报现有数据。
- 不修改自动通报原数据库表。

建议使用独立环境变量：

```env
DASHBOARD_MYSQL_HOST=127.0.0.1
DASHBOARD_MYSQL_PORT=3306
DASHBOARD_MYSQL_DATABASE=dashboard
DASHBOARD_MYSQL_USER=dashboard_app
DASHBOARD_MYSQL_PASSWORD=
DASHBOARD_MYSQL_WRITE_CHUNK_SIZE=2000
```

密码只存放在本地 `.env` 或服务器密钥配置中，不得提交到 Git。
`DASHBOARD_MYSQL_WRITE_CHUNK_SIZE` 控制实时指标批量 SQL 的行数，默认 `2000`，
允许范围为 `1-10000`。出现数据库 I/O 或锁等待时，建议对比测试 `500`、`1000`
和 `2000`，不要直接扩大到最大值。

### 4.2 连接安全

优先使用以下方式连接云服务器 MySQL：

1. 云服务器内网连接。
2. VPN 或专用网络。
3. SSH 隧道。
4. 必须开放公网时，限制固定 IP 白名单并启用 TLS。

不得使用 MySQL `root` 账号作为应用账号。

## 5. 第一阶段数据表

第一阶段先建立以下基础表：

### 5.1 `area`

保存接口返回的分公司、网格和渠道信息。

建议字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 数据库主键 |
| `area_code` | 地市平台区域编码 |
| `area_name` | 区域名称 |
| `level_type` | `BRANCH`、`GRID` 或 `CHANNEL` |
| `branch_code` | 所属分公司编码 |
| `branch_name` | 所属分公司名称 |
| `grid_code` | 所属网格编码 |
| `grid_name` | 所属网格名称 |
| `channel_type` | 渠道类型 |
| `owner_name` | 负责人 |
| `enabled` | 是否有效 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`area_code` 应建立唯一索引。

### 5.2 `indicator`

保存指标定义。

建议字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 指标主键 |
| `code` | 接口指标编码 |
| `name` | 指标名称 |
| `category` | 指标分类 |
| `unit` | 单位 |
| `enabled` | 是否启用 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`code` 应建立唯一索引。

### 5.3 `metric_current`

保存每个区域、每个指标的最新值，用于驾驶舱快速查询。

建议字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 主键 |
| `area_id` | 对应 `area.id` |
| `indicator_id` | 对应 `indicator.id` |
| `collection_run_id` | 产生当前值的最新采集批次 |
| `metric_value` | 最新指标值 |
| `stat_date` | 数据统计日期 |
| `collected_at` | 最近采集时间 |
| `updated_at` | 数据库更新时间 |

建议建立唯一索引：

```text
(area_id, indicator_id)
```

采集时使用 MySQL UPSERT 更新最新值。

### 5.4 `metric_snapshot`

保存需要保留的历史快照，用于趋势及短周期变化计算。

建议字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 主键 |
| `collection_run_id` | 对应 `collection_run.id` |
| `area_id` | 对应 `area.id` |
| `indicator_id` | 对应 `indicator.id` |
| `metric_value` | 本批次指标值 |
| `collected_at` | 采集时间，日期可通过 `DATE(collected_at)` 获取 |

建议索引：

```text
(collection_run_id, area_id, indicator_id)
(area_id, indicator_id, collected_at)
```

历史快照必须设计保留周期或按月分区，不能无限保存全部高频数据。

### 5.5 `collection_run`

保存每次采集任务状态。

建议字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 主键 |
| `batch_no` | 唯一批次号 |
| `started_at` | 开始时间 |
| `finished_at` | 完成时间 |
| `status` | `running`、`success` 或 `failed` |
| `request_count` | 请求次数 |
| `row_count` | 标准化数据行数 |
| `insert_count` | 写入行数 |
| `error_message` | 错误信息 |

## 6. 数据标准化

地市平台一条记录可能包含多个指标：

```json
{
  "areaCode": "AQ701",
  "areaName": "须水网格",
  "sgs_ajvwdz": "10",
  "sgs_ydzjdz": "20"
}
```

写入数据库前转换成长表：

| area | indicator | value |
| --- | --- | ---: |
| AQ701 | sgs_ajvwdz | 10 |
| AQ701 | sgs_ydzjdz | 20 |

标准化流程：

1. 根据 `areaCode` 新增或更新 `area`。
2. 根据指标编码查找 `indicator`。
3. 将字符串数值转换为统一的数值类型。
4. 批量 UPSERT 到 `metric_current`。
5. 按快照策略批量写入 `metric_snapshot`。
6. 更新 `collection_run` 的执行状态。

禁止逐条提交事务，应使用批量写入。

## 7. 采集策略

- 默认每 5 分钟运行一次。
- 同一批次使用唯一 `batch_no`。
- 防止同一任务重复并发执行。
- 接口失败时记录任务状态，不覆盖上一批成功数据。
- 单个区域失败时记录错误，允许按配置决定整批失败或部分成功。
- 写入 `metric_current` 和任务状态应使用事务。
- 采集任务应支持手动运行和 Prefect 定时运行。

## 8. 后端接口

驾驶舱 API 单独放在 `backend/routers/dashboard.py`。

第一阶段建议提供：

```text
GET /api/dashboard/status
GET /api/dashboard/areas
GET /api/dashboard/indicators
GET /api/dashboard/summary
GET /api/dashboard/ranking
GET /api/dashboard/trend
GET /api/dashboard/collection-runs
POST /api/dashboard/collect
```

查询参数可包括：

- `stat_date`
- `indicator_code`
- `level_type`
- `branch_code`
- `grid_code`
- `area_code`
- `minutes`

React 前端只能访问 FastAPI，不得直接连接 MySQL。

## 9. 前端页面

驾驶舱作为自动通报 React 管理端中的独立页面：

```text
/configs      自动通报配置中心
/dashboard    数据驾驶舱
```

建议组件：

```text
pages/dashboard/Dashboard.tsx
components/dashboard/MetricCard.tsx
components/dashboard/TrendChart.tsx
components/dashboard/RankingTable.tsx
components/dashboard/AreaFilter.tsx
components/dashboard/CollectionStatus.tsx
```

第一阶段页面展示：

- 最近更新时间
- 采集任务状态
- 核心指标卡片
- 分公司、网格、渠道筛选
- 指标排名
- 指标趋势
- 5/15/30/60 分钟变化

可以使用 ECharts 实现图表。

```text

  -> master

C:\Users\yuyu\Desktop\项目\可视化通报
```

数据驾驶舱在 `feature/dashboard` 分支开发，完成后合并：

## 12. 实施顺序

### 第一阶段：稳定入库

1. 建立 Worktree 和 `feature/dashboard` 分支。
2. 增加驾驶舱 MySQL 配置及连接检查。
3. 创建 `area`、`indicator`、`metric_current`、`metric_snapshot`、`collection_run`。
4. 配置首批指标。
5. 实现地市平台数据采集。
6. 实现数据标准化和批量写入。
7. 添加手动采集命令及测试。
8. 配置每 5 分钟 Prefect 任务。
9. 验证长时间运行、重复执行和失败恢复。

### 第二阶段：查询与页面

1. 实现汇总、排名和趋势 API。
2. 增加驾驶舱 React 路由和页面。
3. 实现区域和指标筛选。
4. 实现指标卡、排名和趋势图。
5. 增加采集状态和数据更新时间提示。

### 第三阶段：业务计算

按实际需求增加：

- 累计值
- 目标值
- 完成率
- 5/15/30/60 分钟变化
- 日环比和月环比
- 驾驶舱聚合结果
- 历史数据归档与清理

## 13. 验收标准

第一阶段完成标准：

- 自动通报原功能和原数据库不受影响。
- 能复用已有登录会话请求地市平台。
- 采集任务可手动和定时运行。
- 数据可批量写入云服务器 MySQL。
- 同一批数据不会异常重复写入。
- 请求失败不会覆盖最近一次成功数据。
- 可以查询最新指标值和最近采集状态。
- 密码、Token、Cookie 不进入 Git。
- 有基础单元测试和一次真实环境试跑记录。

## 14. 给 Codex 的执行要求

开始开发前先阅读自动通报现有架构和测试。

实施时必须遵守：

- 不迁移自动通报原数据库。
- 不修改自动通报现有数据库连接配置。
- 不重写现有自动登录流程。
- 不把驾驶舱逻辑塞入 Excel 转换服务。
- 优先复用登录、Session 和地市平台请求能力。
- 驾驶舱 MySQL 使用独立配置、连接模块和数据表。
- 每完成一个阶段都运行自动通报原测试，避免功能回归。
- 第一阶段先保证稳定采集和入库，再开发复杂图表。
