# 并发登录与调度异常排查方案

本文用于排查多个 Prefect 调度同时触发时出现的登录、探活、旧浏览器、Cookie 失效和下载失败问题。

## 典型现象

- 多个部署在同一分钟启动，部分流程成功，部分流程失败。
- 日志出现 `已有 Cookie 探活失败，将进入登录锁并在锁内复检`。
- 日志出现 `JSON 接口返回 session 已过期: reCode=1101` 或 `单点登录超时，请登录后重新跳转`。
- 登录页卡在多终端工具弹窗，或出现 `网络环境发生变化 / 安全检查失败`。
- Prefect Work Pool 显示红点，`Last Polled` 很久没有更新。
- `runtime/locks/login.lock` 存在，但实际登录进程已经不在。
- 看起来旧 Edge 没有关闭，或者自动登录又在旧浏览器窗口里继续操作。

## 根因判断

### 1. 同时触发导致登录互相影响

当前系统使用一套自动登录 Cookie。多个流程同时启动时，都会先探活：

1. A 流程发现 Cookie 失效，进入登录锁并重新登录。
2. B 流程可能仍拿着旧 Cookie 继续下载。
3. A 登录成功后，NGBOSS 侧可能让旧 Cookie 失效。
4. B 下载接口返回 `reCode=1101`，于是失败或触发重登。

这类问题不是单个接口错误，而是并发登录和单点会话互相覆盖。

### 2. 探活失败不一定代表马上要由当前流程登录

探活失败后进入登录锁是合理的，但拿到锁以后必须复检一次。原因是：

- 当前流程等待登录锁期间，可能已经有另一个流程完成了登录。
- 如果不复检，每个等待者都会再次登录，导致刚刷新的 Cookie 又被覆盖。

所以推荐逻辑是：

```text
探活失败
  -> 进入登录锁
  -> 锁内重新读取 Cookie 并复检
  -> 复检成功：复用新 Cookie
  -> 复检失败：当前流程负责重新登录
```

### 3. 旧 Edge 没关通常有两种情况

- 看到的是刚刚重新打开的新自动登录 Edge，不是旧进程。
- 打开的 Edge 不属于自动登录 profile，因此关闭逻辑不会处理它。

自动登录浏览器应使用固定 profile，例如：

```json
{
  "browser": {
    "user_data_dir": "runtime/browser_session/edge_profile_auto_login"
  }
}
```

不要手动在这个自动化 Edge 里长期打开业务页面。手动访问其它页面可能改变 Cookie、localStorage、sessionStorage，造成探活和下载使用的认证状态不一致。

### 4. `login.lock` 残留会让流程卡住

如果登录进程被 Ctrl+C、关闭窗口或系统异常中断，`runtime/locks/login.lock` 可能来不及删除。

修复策略：

- lock 文件内记录 PID。
- 等待登录锁时先判断 PID 是否仍存在。
- PID 不存在时立即视为陈旧锁并清理。
- 不再只靠固定超时时间等待。

### 5. 多终端工具弹窗会挡住登录输入框

NGBOSS 登录页可能出现多终端工具提示弹窗，即使本机已经安装也可能弹出。此时需要自动点击“确认”后继续登录。

注意：弹窗外层有遮罩层和 iframe，普通 Selenium click 可能被遮挡，所以应使用 JS click。

## 推荐解决方案

### 方案 A：调度错峰

这是最稳的方案。不要让所有报表都在 `00` 秒同一分钟启动。

示例：

```text
PK赛通报：         0,10,20,30,40,50 分
爱家亲情网每日盯控： 1,11,21,31,41,51 分
爱家营业厅每日盯控： 2,12,22,32,42,52 分
爱家V网：          3,13,23,33,43,53 分
```

优点：

- 最少改代码。
- 减少登录和下载同时争抢。
- 更容易从日志判断是哪一个流程先出问题。

缺点：

- 报表发送时间会有 1 到数分钟偏移。

### 方案 B：保留登录互斥锁，并在锁内复检

登录必须串行，同一时间只能有一个流程执行重新登录。

关键点：

- 探活失败后进入登录锁。
- 拿到锁后重新读取 Cookie 并复检。
- 复检成功就直接复用，不再重复登录。
- 复检失败才关闭旧自动登录浏览器并重新登录。
- 登录后再探活，确认 Cookie 真可用。

这个方案可以避免多个流程连续重复登录。

### 方案 C：下载遇到 session 过期后只重试一次

下载阶段如果接口明确返回 session 过期，可以触发一次强制刷新登录，然后重试下载。

关键点：

- 只对明确的 session 过期重试。
- 网络超时走网络重试，不要当作登录失效。
- 重试次数要有限，避免无限登录。

推荐区分：

```text
ConnectTimeout / ReadTimeout / ConnectionError
  -> 网络重试

reCode=1101 / session_expired / status_not_allowed
  -> 登录刷新后重试一次

字段缺失 / JSON 结构异常 / 权限不足
  -> 直接失败并保留日志
```

### 方案 D：限制同一批流程的并发下载

如果业务接口本身不稳定，或者登录态非常容易被单点登录覆盖，可以进一步加一个“下载保护”。

可选做法：

- 对所有需要同一账号 Cookie 的下载任务加全局锁。
- 或者用 Prefect concurrency limit 限制同类部署同时运行数量。
- 或者只限制登录后的关键下载接口，不限制截图和通知。

优先级建议：

1. 先调度错峰。
2. 再登录锁内复检。
3. 再给 session 过期增加一次刷新重试。
4. 最后才考虑全局下载串行。

## 如何模拟同时触发

### 方法 1：Prefect UI 手动触发

在 Prefect UI 中连续点击多个 Deployment 的 Run，尽量在同一分钟内启动。

观察重点：

- 是否只有一个流程进入真正登录。
- 其它流程是否在锁内复检后复用 Cookie。
- 是否出现多个 Edge 同时登录。
- 是否出现 `reCode=1101`。

### 方法 2：PowerShell 并发触发

在项目根目录执行：

```powershell
$deployments = @(
  "auto-notify-flow/notify-PK赛通报",
  "auto-notify-flow/notify-爱家亲情网每日盯控",
  "auto-notify-flow/notify-爱家亲情网营业厅每日盯控",
  "auto-notify-flow/notify-爱家V网"
)

$deployments | ForEach-Object {
  Start-Job -ScriptBlock {
    param($name)
    python -m prefect deployment run $name
  } -ArgumentList $_
}

Get-Job
Receive-Job *
```

如果 deployment 名称不同，先在 Prefect UI 或部署配置中确认实际名称。

## 验证点

### 1. 登录锁是否正常

预期日志：

```text
已有 Cookie 探活失败，将进入登录锁并在锁内复检
```

如果等待期间其它流程已经登录成功，预期后续看到类似：

```text
锁内复检通过，复用已有 Cookie
```

如果仍失败，才应该出现重新登录。

### 2. 旧浏览器是否被关闭

预期日志应包含关闭结果，例如：

```text
重新登录前已关闭旧自动登录浏览器
```

如果仍看到 Edge，确认它是否属于自动登录 profile：

```text
runtime/browser_session/edge_profile_auto_login
```

不属于这个 profile 的 Edge，不应由自动登录关闭逻辑处理。

### 3. 多终端工具弹窗是否被处理

预期日志：

```text
检测到多终端工具提示弹窗，自动点击确认后继续登录
```

如果没有点击成功，需要保存当时页面：

```text
runtime/login_debug/login_*.html
runtime/login_debug/login_*.png
```

检查按钮是否仍是：

```html
input.msgbox_button[value="确认"]
```

### 4. 网络超时是否被重试

对于 `ConnectTimeout`、`ReadTimeout`、`ConnectionError`，预期应重试，而不是马上失败。

如果重试后成功，说明是临时网络抖动。

如果多次失败，说明接口不可达或网络环境异常。

### 5. Work Pool 是否在线

Prefect Work Pool 红点、`Last Polled` 很久不更新，说明 worker 没有正常轮询。

重新启动：

```powershell
pwsh -File scripts\prefect_start.ps1 -Mode both -Detached
```

只启动 worker：

```powershell
pwsh -File scripts\prefect_start.ps1 -Mode worker -Detached
```

如果使用 public stack：

```powershell
pwsh -File scripts\start_public_stack.ps1 -ForceRestart
```

## 应急处理

### 清理残留登录锁

确认没有登录流程正在运行后再删除：

```powershell
Remove-Item runtime\locks\login.lock -ErrorAction SilentlyContinue
```

### 重启整套服务

```powershell
pwsh -File scripts\public_stack.ps1 -Action start -ForceRestart
```

### 保留现场

出现异常时优先保留：

- Prefect flow run 日志。
- `runtime/login_debug/login_*.html`
- `runtime/login_debug/login_*.png`
- `runtime/locks/login.lock`
- 失败时间点对应的 Edge 页面截图。

## 最终建议

短期建议：

- 部署 Cron 错峰 1 到 3 分钟。
- 保留登录锁和锁内复检。
- 下载网络请求增加有限重试。
- 登录前关闭自动登录 profile 对应的旧 Edge。
- 多终端工具弹窗自动确认。

长期建议：

- 将同一账号下的下载任务纳入统一并发控制。
- 区分网络失败、登录失效、权限失败和数据结构失败。
- 给登录刷新、Cookie 写入、下载开始三个节点增加结构化日志。
- 自动登录 Edge 只用于系统脚本，不手动打开业务页面。
