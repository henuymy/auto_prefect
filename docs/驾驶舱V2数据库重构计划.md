# 驾驶舱 V2 数据库重构计划

## 1. 建设目标

在远端 MySQL `49.233.78.70:3306` 新建全新的 `dashboard` 数据库，不沿用旧数据库表结构。重构后必须保留现有采集、结构漂移检测、实时值、历史快照、累计指标、定制指标、目标值、完成率、排序、搜索和前端下钻功能，并新增渠道经理正式层级及指标。

Prefect 的 PostgreSQL 状态库继续独立维护，不合并到 Dashboard MySQL。

完整当前树统一保存为：

```text
CITY
└─ BRANCH
   └─ GRID
      └─ CHANNEL_MANAGER
         └─ CHANNEL
```

层级策略：

| 层级 | 发请求 | 落指标 | 快照策略 |
| --- | ---: | ---: | --- |
| CITY | 是 | 是 | 每批全量 |
| BRANCH | 是 | 是 | 每批全量 |
| GRID | 是 | 是 | 每批全量 |
| CHANNEL_MANAGER | 是 | 是 | 每批全量 |
| CHANNEL | 否 | 是 | 数值变化或每日检查点 |

## 2. 最终业务表

| 表名 | 作用 |
| --- | --- |
| `hierarchy_node` | 保存当前完整组织树 |
| `hierarchy_parent_history` | 保存节点历史归属 |
| `indicator` | 保存来源指标和定制指标目录 |
| `indicator_formula_component` | 保存定制指标公式组成 |
| `target_plan` | 保存目标方案、场景和有效期 |
| `metric_target_value` | 保存节点和指标的具体目标值 |
| `collection_run` | 保存每次采集批次及执行状态 |

Alembic 自动创建的 `alembic_version` 不属于业务表。

## 3. 组织结构表

### 3.1 `hierarchy_node`

该表是当前树结构的唯一权威来源，取代原来的 `area`、`request_target` 和 `channel_manager_area`。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 节点主键 |
| `node_type` | VARCHAR(32) | 节点类型：CITY、BRANCH、GRID、CHANNEL_MANAGER、CHANNEL |
| `node_code` | VARCHAR(100) | 上游节点编码，使用区分大小写的排序规则 |
| `node_name` | VARCHAR(200) | 节点名称 |
| `parent_id` | BIGINT UNSIGNED NULL | 当前父节点 ID，CITY 为 NULL |
| `level_no` | TINYINT UNSIGNED | 层级序号 1～5 |
| `request_enabled` | BOOLEAN | 是否作为上游接口请求目标 |
| `metric_enabled` | BOOLEAN | 是否参与指标覆盖校验和指标落库 |
| `enabled` | BOOLEAN | 当前是否有效 |
| `sort_order` | INT UNSIGNED | 展示排序 |
| `last_seen_at` | DATETIME(3) NULL | 最近一次可信采集发现时间 |
| `missing_count` | INT UNSIGNED | 连续可信采集未发现次数 |
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

约束与索引：

```text
UNIQUE(node_type, node_code)
INDEX(parent_id, enabled, sort_order)
INDEX(node_type, enabled, sort_order)
INDEX(request_enabled, enabled)
INDEX(metric_enabled, enabled)
```

父级规则由结构校验服务强制执行：

```text
CITY            → 无父级
BRANCH          → CITY
GRID            → BRANCH
CHANNEL_MANAGER → GRID
CHANNEL         → CHANNEL_MANAGER
```

任何节点不得同时存在两个当前父级，不得形成循环，启用节点不得挂在停用父节点下。

### 3.2 `hierarchy_parent_history`

保存节点过去的父级关系，用于还原渠道换经理、经理换网格之前的历史树。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 关系历史主键 |
| `child_node_id` | BIGINT UNSIGNED | 子节点 ID |
| `parent_node_id` | BIGINT UNSIGNED | 父节点 ID |
| `valid_from` | DATETIME(3) | 关系开始生效时间 |
| `valid_to` | DATETIME(3) NULL | 关系失效时间，NULL 表示当前有效 |
| `collection_run_id` | BIGINT UNSIGNED NULL | 发现此次变化的采集批次 |
| `change_type` | VARCHAR(32) | CREATED、MOVED、RESTORED |
| `active_child_node_id` | BIGINT UNSIGNED GENERATED | `valid_to IS NULL` 时等于 `child_node_id`，否则为 NULL |
| `created_at` | DATETIME(3) | 记录创建时间 |

主要索引：

```text
INDEX(child_node_id, valid_from, valid_to)
INDEX(parent_node_id, valid_from, valid_to)
UNIQUE(active_child_node_id)
```

`active_child_node_id` 的 MySQL 定义为 `GENERATED ALWAYS AS (CASE WHEN valid_to IS NULL THEN child_node_id ELSE NULL END) STORED`。MySQL 唯一索引允许多个 NULL，但不允许同一个非 NULL 子节点重复，因此可以从数据库层保证每个子节点最多一条当前关系。

`collection_run_id` 外键使用 `ON DELETE SET NULL`。当前关系、历史关系和指标写入必须在同一事务提交。节点换父级时先关闭旧关系，再建立新关系，最后更新 `hierarchy_node.parent_id`。

## 4. 指标配置表

### 4.1 `indicator`

统一保存上游来源指标和用户定制指标。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 指标主键 |
| `code` | VARCHAR(100) | 指标编码，区分大小写且唯一 |
| `name` | VARCHAR(200) | 指标名称 |
| `indicator_type` | VARCHAR(16) | SOURCE 或 CUSTOM |
| `storage_mode` | VARCHAR(16) | STORE 或 COMPONENT |
| `enabled` | BOOLEAN | 是否启用 |
| `source_active` | BOOLEAN | 上游是否仍提供该指标 |
| `sort_order` | INT UNSIGNED | 展示顺序 |
| `removed_at` | DATETIME(3) NULL | 上游移除时间 |
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

`SOURCE` 表示上游直接返回，`CUSTOM` 表示公式计算；`STORE` 表示正式展示落库，`COMPONENT` 表示仅作为公式来源。

### 4.2 `indicator_formula_component`

保存定制指标的加权公式。例如：`C = A × 1.5 + B × -1`。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 公式明细主键 |
| `custom_indicator_id` | BIGINT UNSIGNED | 定制指标 ID |
| `source_indicator_id` | BIGINT UNSIGNED | 来源指标 ID |
| `coefficient` | DECIMAL(20,4) | 计算系数 |
| `sort_order` | INT UNSIGNED | 公式项顺序 |
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

约束：

```text
UNIQUE(custom_indicator_id, source_indicator_id)
```

公式不能为空，不能引用自身，不允许循环依赖。定制指标目标默认由组成指标目标按系数计算，不重复保存一份可能不一致的直接目标。

## 5. 目标值表

### 5.1 `target_plan`

定义目标方案、目标场景、目标周期和生效时间。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 目标方案主键 |
| `plan_name` | VARCHAR(200) | 方案名称 |
| `scenario` | VARCHAR(16) | NORMAL 或 PK |
| `period_type` | VARCHAR(16) | DAY 或 MONTH |
| `effective_from` | DATE | 开始生效日期 |
| `effective_to` | DATE NULL | 结束生效日期 |
| `priority` | INT | 多方案同时命中时的优先级 |
| `version_no` | INT UNSIGNED | 同类方案版本号 |
| `status` | VARCHAR(16) | DRAFT、ACTIVE 或 RETIRED |
| `supersedes_plan_id` | BIGINT UNSIGNED NULL | 本版本替代的旧方案 |
| `activated_at` | DATETIME(3) NULL | 激活时间 |
| `retired_at` | DATETIME(3) NULL | 退役时间 |
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

四类目标值：

| scenario | period_type | 中文含义 |
| --- | --- | --- |
| NORMAL | DAY | 正常时期日目标值 |
| NORMAL | MONTH | 正常时期月目标值 |
| PK | DAY | PK 赛时期日目标值 |
| PK | MONTH | PK 赛时期月目标值 |

约束和索引：

```text
CHECK(scenario IN ('NORMAL', 'PK'))
CHECK(period_type IN ('DAY', 'MONTH'))
CHECK(status IN ('DRAFT', 'ACTIVE', 'RETIRED'))
CHECK(effective_to IS NULL OR effective_to >= effective_from)
UNIQUE(scenario, period_type, plan_name, version_no)
INDEX(scenario, period_type, status, effective_from, effective_to, priority)
```

只有 DRAFT 方案允许修改方案内容和目标值。ACTIVE 方案及其 `metric_target_value` 启用后不可原地修改；需要调整时复制为新版本，设置 `supersedes_plan_id`，完成校验后再激活。旧版本退役时只允许在同一事务中设置 `status=RETIRED`、`retired_at` 及必要的 `effective_to=新版本 effective_from - 1 天`，不允许改动已生效日期段内的其他字段或目标值。

激活时在事务内锁定同 `scenario + period_type` 的方案，校验有效期重叠和优先级冲突。目标查询按业务日期在 ACTIVE 和 RETIRED 版本中匹配有效期，不查询 DRAFT；同一天命中多个候选方案时，先选择 `priority` 最高的方案，优先级相同则选择 `effective_from` 最新的方案，仍无法唯一确定时拒绝激活。历史完成率固定使用当时不可变方案，不使用后来版本重算。`supersedes_plan_id` 是指向旧方案的自关联外键，使用 `ON DELETE RESTRICT`。

### 5.2 `metric_target_value`

保存目标方案中每个节点、每个指标的具体目标值。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 目标值主键 |
| `plan_id` | BIGINT UNSIGNED | 所属目标方案 ID |
| `node_id` | BIGINT UNSIGNED | 组织节点 ID |
| `indicator_id` | BIGINT UNSIGNED | 指标 ID |
| `target_value` | DECIMAL(20,4) | 目标值 |
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

约束：

```text
UNIQUE(plan_id, node_id, indicator_id)
```

`plan_id` 外键可使用 `ON DELETE CASCADE`，但仅 DRAFT 方案允许物理删除；ACTIVE 和 RETIRED 方案只允许状态流转，不物理删除。`node_id` 和 `indicator_id` 使用 `ON DELETE RESTRICT`。

实时和日累计页面读取 DAY 目标，月累计页面读取 MONTH 目标。先判定业务日期是否命中 PK 方案有效期：命中则只读取 PK 目标，未命中才读取 NORMAL 目标。PK 方案存在但某节点或指标目标值缺失时，不自动回退到 NORMAL，避免使用错误口径。无目标值的指标不参与完成率和目标排序。

## 7. 指标事实表

### 7.1 `metric_current`

每个节点、每个指标只保留最新值。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 |
| `node_id` | BIGINT UNSIGNED | 节点 ID |
| `indicator_id` | BIGINT UNSIGNED | 指标 ID |
| `collection_run_id` | BIGINT UNSIGNED NULL | 来源采集批次，批次清理后可为 NULL |
| `metric_value` | DECIMAL(20,4) | 当前指标值 |
| `stat_date` | DATE | 指标业务日期 |
| `collected_at` | DATETIME(3) | 实际采集时间 |
| `updated_at` | DATETIME(3) | 更新时间 |

约束：

```text
UNIQUE(node_id, indicator_id)
```

每批全量更新所有指标节点，且只允许较新的 `collected_at` 覆盖旧值。`collection_run_id` 外键使用 `ON DELETE SET NULL`。按当前约 4717 个指标节点、8 个落库指标计算，每批约写 37736 行。

### 7.2 `metric_snapshot`

保存实时指标历史快照。

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 快照 ID |
| `collection_run_id` | BIGINT UNSIGNED | 来源采集批次 |
| `node_id` | BIGINT UNSIGNED | 节点 ID |
| `indicator_id` | BIGINT UNSIGNED | 指标 ID |
| `metric_value` | DECIMAL(20,4) | 快照值 |
| `collected_at` | DATETIME(3) | 快照采集时间，也是分区键 |

约束和索引：

```text
PRIMARY KEY(id, collected_at)
UNIQUE(collection_run_id, node_id, indicator_id, collected_at)
INDEX(node_id, indicator_id, collected_at)
INDEX(collected_at)
```

该表按 `collected_at` 每日分区，`id` 为 AUTO_INCREMENT 且位于复合主键首列。表不建立外键，`collection_run_id/node_id/indicator_id` 使用逻辑引用和应用校验。默认保留 7 天。CITY、BRANCH、GRID、CHANNEL_MANAGER 每批完整写入；CHANNEL 仅在首次出现、数值变化或每日首次采集时写入。历史查询对稀疏渠道读取目标时间之前最后一条值。

稳定批次最低快照量约为：

```text
(1 CITY + 16 BRANCH + 146 GRID + 537 CHANNEL_MANAGER) × 8
= 5600 行 + 渠道变化行
```

| 字段 | 类型 | 中文含义 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 |
| `period_type` | VARCHAR(16) | DAY_ACC 或 MONTH |
| `stat_date` | DATE | 统计日期或月末日期 |
| `node_id` | BIGINT UNSIGNED | 节点 ID |
| `indicator_id` | BIGINT UNSIGNED | 指标 ID |
| `collection_run_id` | BIGINT UNSIGNED NULL | 来源采集批次，批次清理后可为 NULL |

| `collected_at` | DATETIME(3) | 采集时间 |

`collection_run_id` 外键使用 `ON DELETE SET NULL`。同一唯一键发生重放或乱序采集时，只有新值 `collected_at >= 已存值 collected_at` 才允许更新 `metric_value`、`collection_run_id` 和 `collected_at`。

## 8. 结构发现和结构漂移

每批采集先读取 `hierarchy_node` 构建当前树，再根据本批响应构建内存观察树。结构对比必须覆盖：

- 新增城市、分局、网格、渠道经理和渠道；
- 节点名称变化和停用节点恢复；
- 节点消失；
- 渠道经理换网格；
- 渠道换经理；
- 多父级、错误父级和循环关系。

处理流程：

```text
首次采集
→ 构建观察树
→ 与当前树比较
→ 无漂移则进入指标验证
→ 有漂移则暂不写库
→ 只重采受影响网格和渠道经理
→ 构建候选树
→ 验证通过后原子提交结构、关系历史和指标
```

请求错误不能作为节点删除依据。只有父节点请求成功且子节点连续两次可信采集都未出现时，才停用子节点。节点在其他父级下出现时按迁移处理，不按删除处理。

新渠道经理由网格响应发现，加入候选请求目标后重采经理，取得经理自身汇总行和下属渠道；新渠道由经理响应发现。新节点确认后，在同一事务中写入 `hierarchy_node`、`hierarchy_parent_history`、指标事实表和批次状态。

空库首次启动采用初始化模式。CITY、BRANCH、GRID 不能从空的 `hierarchy_node` 自动发现，必须先从经审核的基础结构清单导入；然后请求网格发现经理，请求经理发现渠道。完整树和首批指标校验通过后才启用 5 分钟定时任务。

### 8.1 空库初始化协议

基础结构清单来自上游组织导出或经业务确认的配置文件，不直接复制旧数据库中未经校验的关系。清单每行固定包含：

```text
node_type, node_code, node_name, parent_node_code, sort_order
```

初始化步骤：

1. 校验只包含 CITY、BRANCH、GRID，节点编码非空且在同类型中唯一。
2. 校验 CITY 无父级、BRANCH 父级为 CITY、GRID 父级为 BRANCH，无断链和循环。
3. 在单一事务中按 CITY → BRANCH → GRID 顺序写入 `hierarchy_node` 和初始 `hierarchy_parent_history`，这三类节点默认 `request_enabled=1`、`metric_enabled=1`。
4. 提交后重读数据库生成 `current_graph`，与输入清单逐节点比对；不一致时不进入发现阶段。
5. 请求全部 GRID 发现 CHANNEL_MANAGER，再请求全部 CHANNEL_MANAGER 发现 CHANNEL 和经理自身指标。
6. 构建完整 `candidate_graph`，通过覆盖、唯一父级和无循环校验后，在最终业务事务中写入经理、渠道和首批指标。

初始化任一请求失败都不得通过“缺失阈值”停用基础节点。重试初始化时复用已确认的基础节点，不创建重复 ID。

## 9. 渠道经理指标解析

渠道经理请求返回的数据按以下规则处理：

- `areaCode == target_code` 的唯一汇总行作为渠道经理自身指标；
- 其他有效行作为其下属渠道指标；
- 经理自身汇总行缺失或重复时，该请求失败；
- 经理指标使用上游直接值，不用下属渠道求和伪造；
- GRID 响应负责确认 GRID → CHANNEL_MANAGER 结构；经理响应负责确认 CHANNEL_MANAGER → CHANNEL 结构。

## 10. API 和前端字段

前端直接使用 V2 数据库语义字段，不再保留 `area_*` 兼容字段，也不增加字段映射层。

- 组织节点统一使用 `id`、`node_code`、`node_name`、`node_type`、`parent_id`。
- 指标、目标和历史数据关联节点时统一使用 `node_id`。
- 删除 API 和前端中的 `area_id`、`area_code`、`area_name`、`level_type` 旧字段依赖。
- API 路由、HTTP 方法、业务功能、查询口径、排序和分页原则上保持不变；涉及组织节点的请求参数和响应 DTO 一次性切换到 V2 字段。
- 原网格直接下钻渠道的功能保留；新增完整树模式，支持分局 → 网格 → 渠道经理 → 渠道。
- matrix、history、current、acc、target 和 drill-down 查询增加 CHANNEL_MANAGER，原 CITY、BRANCH、GRID、CHANNEL 业务能力不变。

组织节点响应示例：

```json
{
  "id": 167,
  "node_code": "AR060L",
  "node_name": "某渠道",
  "node_type": "CHANNEL",
  "parent_id": 42
}
```

### 10.1 统一树查询示例

V2 查询“某网格下的所有渠道”直接对 `hierarchy_node` 自连接，不再读取 `area`、`request_target` 和 `channel_manager_area`：

```sql
SELECT channel.id,
       channel.node_code,
       channel.node_name,
       channel.node_type,
       channel.parent_id
FROM hierarchy_node manager
JOIN hierarchy_node channel
  ON channel.parent_id = manager.id
WHERE manager.parent_id = :grid_node_id
  AND manager.node_type = 'CHANNEL_MANAGER'
  AND manager.enabled = 1
  AND channel.node_type = 'CHANNEL'
  AND channel.enabled = 1;
```

请求目标同样直接查询 `hierarchy_node` 中 `request_enabled=1` 的 CITY、BRANCH、GRID 和 CHANNEL_MANAGER。

### 10.2 API 改造边界

- 不推倒重写所有 API，仅修改组织节点 DTO、节点参数名和底层查询实现。
- 前端 TypeScript 类型、API 客户端、状态管理、缓存 key 和组件 props 统一使用 V2 字段，不长期同时保留两套字段。
- 渠道经理下钻、经理自身指标和四类目标选择按现有路由设计增加必要参数；只有语义无法在现有路由表达时才新增路由。
- 切换前对每个 API 执行 V2 契约测试，校验 HTTP 状态码、V2 字段、类型、空值、树归属、排序、分页和数值口径。

## 11. 重构原则与必须继承的机制

历史实现只作为业务行为和可靠性机制的验证来源，不要求复制原表结构或原代码组织。V2 实施遵循以下原则：

1. **功能不变**：REALTIME、DAY_ACC、MONTH、多指标、定制指标、目标、完成率、排序、历史和下钻能力全部保留。
2. **前后端字段统一**：节点 DTO 直接使用 V2 的 `id/node_code/node_name/node_type/parent_id`，事实数据使用 `node_id`，不增加 `area_*` 兼容映射。
3. **当前树单一权威来源**：`hierarchy_node` 是当前树的唯一权威表，不再并行维护 `area/request_target/channel_manager_area` 三套状态。
4. **当前与历史分离**：当前父级读 `parent_id`，过去归属读 `hierarchy_parent_history`，两者不混用。
5. **请求资格与指标资格分离**：`request_enabled` 决定是否向上游发请求，`metric_enabled` 决定是否落指标；渠道不发请求但必须落指标。
6. **节点 ID 稳定**：改名、迁移、停用和恢复都保留原 ID，不使用删除后新建来表示业务变化。
7. **失败时保守**：请求失败、响应不完整和候选树未通过时不删节点、不改结构、不写事实表。
8. **事务原子性**：结构、父级历史、指标和批次最终状态一次提交，禁止出现半棵新树或只写 current 未写批次的状态。
9. **存储策略按节点类型决定**：渠道稀疏，CITY、BRANCH、GRID 和 CHANNEL_MANAGER 全量，不根据行数或请求来源临时猜测。
10. **幂等、可回滚、可观测**：所有写入有唯一键和时间保护，所有切换有回退路径，所有批次有结构、行数、耗时和失败阶段统计。
11. **真实 MySQL 验证**：SQLite 只用于快速单元测试，分区、外键、锁等待、死锁、迁移和批量 upsert 必须在与生产同版本的 MySQL 验证。
12. **分阶段替换**：先加 V2 存储和适配层，再影子验证，最后切换；在观察期结束前不删除旧库和 legacy 路径。

### 11.1 结构漂移不可退化清单

V2 可以更换表和仓储实现，但不得改变以下判定顺序和保护规则：

1. `current_graph` 只从已提交的 `hierarchy_node` 读取，不得与本批未确认数据混合。
2. `observed_graph` 只由本轮请求成功返回的结构构建；超时、业务失败或响应不完整的子树不具备删除证据。
3. 首轮发现漂移时不写任何结构和指标，先计算受影响 GRID 集合。
4. 默认只重采受影响 GRID 子树；子树范围无法可信确定时才升级为全量重采。
5. 二轮成功后用二轮结果替换对应子树，不得将该子树首轮的 `recoverable_errors` 继续带入候选树。
6. `candidate_graph` 必须通过完整性、唯一父级、父级类型、无循环和指标覆盖校验后才能入库。
7. 新父级下出现的旧节点优先判定为迁移，不得先删除后新建；节点 ID 必须稳定。
8. 只有父节点请求成功且子节点连续两次未出现时才能停用；任意未恢复错误都必须中断删除判定。
   `missing_count` 每个不同 `batch_no` 最多递增一次，同一批内的首轮、子树重试和事务重试不得重复计数。
9. 节点恢复时复用原 ID，清零 `missing_count`，重建当前父级历史，不创建重复节点。
10. 结构、父级历史、指标事实和 `collection_run` 状态在同一个 MySQL 事务中提交；任一阶段失败全部回滚。
11. 稳定节点和稳定关系不发出无效 `UPDATE`，只在名称、父级、启用状态、缺失次数或归属真实变化时写库。
12. 每次漂移必须保留变化数量、样例节点、受影响 GRID、重试策略和失败阶段，便于事后审计。

### 11.2 V2 对漂移类型的统一表达

| 变化 | `hierarchy_node` | `hierarchy_parent_history` | 指标处理 |
| --- | --- | --- | --- |
| 新渠道经理 | 新建 CHANNEL_MANAGER | 新建 GRID 归属 | 二轮重采成功后落经理自身指标 |
| 新渠道 | 新建 CHANNEL | 新建经理归属 | 写 current，按稀疏规则写 snapshot |
| 经理换网格 | 保留原 ID，更新 `parent_id` | 关闭旧记录并建立新记录 | 指标连续，不重建 current |
| 渠道换经理 | 保留原 ID，更新 `parent_id` | 关闭旧记录并建立新记录 | 指标连续，历史归属按时间查询 |
| 节点连续缺失 | 达阈值后 `enabled=0` | 关闭当前关系 | 保留历史指标，不物理删除 |
| 停用节点恢复 | 复用原 ID 并启用 | 新增 RESTORED 关系 | 继续原指标时间线 |

## 12. 分阶段修改计划

以下是实施顺序，不得跳过前一阶段的验收门槛直接切换生产。

### 阶段 0：固化现有行为基线

- 以切换开发前的当前主分支为旧版基线，保留明确的可回退 tag/branch。
- 导出现有 API 请求和响应样例，特别是 matrix、history、current、acc、target 和 drill-down。
- 记录当前启用节点、请求目标、指标数、current 行数、快照减量比和单批耗时。
- 将现有结构漂移测试全部列为 V2 必须通过的回归测试，不允许删除测试来让新实现通过。

验收门槛：现有后端测试、真实 MySQL 集成测试、前端类型检查和生产构建全部通过。

### 阶段 1：建立独立 V2 空库基线

计划新增独立 V2 ORM 和 Alembic 迁移链，一次性创建本文的 10 张业务表。旧迁移链保留为 legacy，不在 V2 空库上执行。

计划涉及：

- `models/`：V2 统一结构、指标、目标和批次模型；
- `migrations/dashboard_v2/`：不可变的空库基线及后续增量迁移；
- `alembic_dashboard_v2.ini`：独立迁移入口；
- 集成测试：从空库 upgrade，downgrade 再 upgrade，校验索引、外键、唯一约束、生成列和分区。

验收门槛：V2 迁移仅在名称为 test/ci 的临时库通过，临时库的 MySQL 主次版本必须与目标生产库一致，不连接生产地址。CI 可额外保留 MySQL 8.4 验证，但不能代替目标版本验证。

### 阶段 2：建立统一树仓储适配层

- 将 `hierarchy_node` 适配为现有采集器所需的 `CollectionTarget`，只加载 `request_enabled=1` 的 CITY、BRANCH、GRID 和 CHANNEL_MANAGER。
- 将 `hierarchy_node` 适配为现有漂移算法所需的 `StructureGraph`，保留已经验证过的对比语义。
- 在服务层校验层级类型、唯一父级、无循环、启用节点的父级也必须启用。
- 父级变化时先关闭旧历史、再新建当前历史、最后更新 `parent_id`，三者必须在同一事务。

验收门槛：新增、改名、换父级、连续缺失、停用恢复、多父级和循环全部有单元测试及 MySQL 事务测试。

### 阶段 3：改造采集解析和结构漂移

计划重点复核 `services/dashboard_collection_service.py`、`services/dashboard_collection_orchestrator.py` 和 `services/dashboard_pipeline.py`：

- 渠道经理请求中，`areaCode == target_code` 的唯一行转换为 CHANNEL_MANAGER 指标行，其余有效行转换为 CHANNEL 指标行；
- GRID 响应只建立 GRID → CHANNEL_MANAGER 观察，经理响应只建立 CHANNEL_MANAGER → CHANNEL 观察；
- 漂移算法继续使用三张图和受影响 GRID 子树重采，仅替换旧表读写适配器；
- 空库初始化作为独立状态机，不将“当前树为空”误判为普通全量删除；
- 结构未通过时不调用任何事实表写入。

验收门槛：将现有全部结构漂移场景在 V2 重放，并增加经理自身指标缺失/重复的失败测试。

### 阶段 4：改造指标写入与稀疏历史

- `metric_current` 每批对所有 `metric_enabled=1` 节点更新，但保留 `collected_at` 保护，较旧批次不得覆盖较新数据。
- CITY、BRANCH、GRID、CHANNEL_MANAGER 每批全量写 `metric_snapshot`。
- CHANNEL 仅在新增、数值变化或跨日检查点时写 `metric_snapshot`。
- 稀疏判定按节点类型进行，不按请求目标类型推测，避免把经理误当渠道。
- REALTIME 写 current + snapshot；DAY_ACC 和 MONTH 写 `metric_acc`；定制指标仍按组成公式计算后落库。
- `metric_acc` 也按 `collected_at` 执行乱序保护，较旧的重放批次不得覆盖同一 `period_type + stat_date + node_id + indicator_id` 的较新值。
- 保留多值分块写入、分块大小配置、写入吞吐统计和慢分块告警。

验收门槛：稳定批次中经理指标必须全量落快照，渠道减量比符合实际变化比例，且不得出现 current 缺失。

### 阶段 5：改造目标、查询和 API V2 字段层

- 目标值改为 `target_plan + metric_target_value`，严格区分 NORMAL/PK 和 DAY/MONTH。
- 目标方案按 DRAFT → ACTIVE → RETIRED 管理，ACTIVE 方案和目标值不可原地修改，历史查询固定使用当时版本。
- 历史查询对渠道使用“目标时刻之前最后一条”，其他层级直接读完整快照；查询层屏蔽两种存储差异。
- API 和前端节点字段一次性切换为 `id/node_code/node_name/node_type/parent_id`，指标关联使用 `node_id`，不保留 `area_*` 映射层。
- 原“网格直接查渠道”继续支持，新增完整的网格 → 经理 → 渠道查询模式。
- 历史归属查询根据 `hierarchy_parent_history` 的有效时间判定，不用当前 `parent_id` 解释过去数据。

验收门槛：V2 API 字段契约和前端类型检查通过；四类目标、完成率、排序、变化量和历史回放与旧版业务口径一致。

### 阶段 6：前端增加经理层但保留原交互

- 组织选择、面包屑、矩阵、排序、搜索和返回导航增加 CHANNEL_MANAGER。
- 原网格页可按兼容模式继续平铺渠道，完整树模式先展示经理。
- 经理层支持实时、日累计、月累计、历史、目标、完成率、多指标和定制指标。
- 不删除现有路由。前端本地缓存和用户配置增加 `schema_version=2`；旧配置同时保存节点编码时，通过 `node_code + node_type` 在新树中恢复选择，只保存旧 `area_id` 时清空该选择，禁止将旧自增 ID 直接当作新 `id`。

验收门槛：TypeScript 类型检查、Vite 生产构建和 CITY 到 CHANNEL 的全链路交互回归通过。

### 阶段 7：影子运行、切换和清理

- 不让一个采集批次同时写两库；使用独立 V2 验证部署运行影子采集，避免分布式半成功。
- 对比新旧库的树、经理归属、current、累计值、目标、API 响应和性能。
- 切换窗口暂停旧定时任务，等待在途批次结束，执行一次 V2 完整采集并验证后再启用 V2 调度。
- 保留旧库、旧配置和 legacy 代码至少 7 天，只读不删除。
- 7 天内任一严重不一致立即停止 V2 调度并回退环境变量，不在新库上做紧急人工改数据。
- 回滚时旧库可能已落后，恢复旧连接后必须在保持 schedule 暂停的状态下先执行一次 REALTIME，再按当前业务日期补采 DAY_ACC 和 MONTH，验证成功后才恢复旧调度。

## 13. 数据库操作机制

### 13.1 连接、账号和连接池

- 应用只通过 `DASHBOARD_MYSQL_*` 环境变量取得连接信息，密码不写入代码、JSON、Markdown、日志或 Git。
- 迁移、采集、查询和分区维护共用一个 Dashboard 专用账号。该账号不使用 root，权限只限定在 `dashboard.*`，不授予全局权限和 `GRANT OPTION`。
- 专用账号需要 `dashboard.*` 范围内的 SELECT、INSERT、UPDATE、DELETE、CREATE、ALTER、DROP、INDEX 和 REFERENCES 权限，用于 Alembic 迁移、日分区维护和日常读写。
- 连接池保留 `pool_pre_ping`、`pool_recycle`、`pool_size`、`max_overflow`、连接超时和读写超时配置。
- 连接建立后验证 `DATABASE()`、MySQL 版本、字符集、时区和当前账号；发现连错库或使用 root 时 readiness 失败。
- 统一使用 `utf8mb4`；节点编码和指标编码列使用区分大小写的排序规则，名称列使用适合中文查询的排序规则。

### 13.2 迁移和数据库结构漂移检查

- 应用启动时不自动 `create_all`、不自动改表；仅由独立 Alembic 命令执行 DDL。
- readiness 必须检查 V2 Alembic revision 是否为期望 head，并检查关键表、列、唯一约束、外键、索引和 `metric_snapshot` 分区是否存在。
- revision 不匹配或关键结构不完整时，后端可以存活但不就绪，Worker 不得开始采集。
- 迁移脚本一旦提交不得因 ORM 后续变化而改变；禁止在基线迁移中动态调用当前 metadata 创建所有表。
- 生产迁移前在同 MySQL 版本的临时库完成 upgrade/downgrade/upgrade 演练，记录 DDL 耗时和锁影响。

DDL 必须显式声明每个字段的 NULL/NOT NULL、DEFAULT、CHECK、外键及 `ON DELETE` 策略，不使用数据库隐式默认。统一外键策略：

- 结构、指标、公式和目标的主数据外键使用 `RESTRICT`，不允许删除仍被业务数据引用的记录。
- `hierarchy_parent_history`、`metric_current`、`metric_acc` 的 `collection_run_id` 可为 NULL，并使用 `ON DELETE SET NULL`。
- `metric_snapshot` 因 MySQL 分区限制不设外键，但写入前必须校验批次、节点和指标存在。
- 所有业务主数据默认逻辑停用，不通过物理删除处理组织或指标变化。

### 13.3 批次互斥和锁顺序

一个完整采集批次使用两层互斥：

1. 本机文件锁：防止同一机器上多进程重复运行。
2. MySQL `GET_LOCK`：防止多台 Worker 或多个 Prefect 调度实例同时写 Dashboard 库。

MySQL 命名锁必须在一条专用连接上持有，在 `finally` 中释放。未取得锁时本批直接失败，不带锁降级执行。

事务内统一锁顺序：

```text
hierarchy_node（按 level_no, node_code）
→ hierarchy_parent_history（按 child_node_id）
→ metric_current（按 node_id, indicator_id，FOR UPDATE）
→ metric_snapshot / metric_acc
→ collection_run 最终状态
```

所有写入路径必须遵守同一顺序，不允许查询到什么顺序就更新什么顺序。

### 13.4 批次状态和事务边界

`collection_run` 分为两类事务：

- 生命周期事务：批次开始时独立创建 `PENDING`，随采集阶段更新为 `RUNNING`；这使外部即使在业务事务回滚后仍能看到失败批次。
- 最终业务事务：通过验证后，结构更新、父级历史、current、snapshot/acc 和 `status=SUCCESS, phase=COMPLETED` 一次提交。

最终事务失败时先回滚所有业务写入，再使用独立短事务把批次更新为 `FAILED`，保存失败阶段和脱敏错误。不允许指标已提交但批次仍显示 RUNNING。

超时批次恢复只能在新进程已成功取得全局 MySQL 命名锁后执行。因为同一时刻不可能再有正常批次持有该锁，此时才可将超过阈值的 `PENDING/RUNNING` 收口为 `FAILED`。不尝试通过批次号反查 MySQL 命名锁持有者。

### 13.5 幂等性和并发保护

- `collection_run.batch_no` 唯一，同一批次号不得重复创建。
- `metric_current` 使用 `UNIQUE(node_id, indicator_id)` 幂等 upsert，只有新批次 `collected_at >= 当前 collected_at` 时才更新，防止乱序批次覆盖新值。
- `metric_snapshot` 使用包含批次、节点、指标和采集时间的唯一约束，同一批次重放不得产生重复快照。
- `metric_acc` 使用 `UNIQUE(period_type, stat_date, node_id, indicator_id)` 幂等 upsert。
- 当前父级历史使用生成列 `active_child_node_id` 及唯一索引，保证一个子节点最多一条 `valid_to IS NULL` 记录，不只依赖应用检查。

### 13.6 死锁、锁等待和重试

- 只对 MySQL 死锁和锁等待超时执行有界重试，默认最多 3 次，采用退避加随机抖动。
- 每次重试必须先完整 rollback，再从“加载当前树和 current”开始重建本次事务，不复用旧 Session 中的 ORM 对象。
- 参数错误、约束错误、覆盖不完、结构漂移未验证、权限错误和迁移版本不匹配不重试。
- 重试日志记录 MySQL 错误码、attempt、退避时间和当前 phase，不记录 SQL 参数中的敏感数据。

### 13.7 批量写入和稀疏快照

- 指标先在内存中规范化并按唯一键去重，覆盖校验通过后再生成 SQL。
- MySQL 使用多值 INSERT/UPSERT 并分块执行；默认 `chunk_size=2000`，配置只允许在已设定的安全范围内。
- 稀疏判定前按 `(node_id, indicator_id)` 固定顺序锁定对应 current 行，避免并发批次同时判定“未变化”。
- 先根据旧 current 生成 snapshot 计划，再插入 snapshot，最后 upsert current；三步位于同一事务。
- “每日检查点”以 `Asia/Shanghai` 业务日期为边界，以渠道当日首次成功 REALTIME 采集为检查点。分区裁剪后，保留窗口内每个业务日都必须至少有一个可用检查点。
- 每批记录输入行数、快照插入/跳过行数、经理全量行数、渠道新增/变化/检查点/未变化数、减量比、分块数、最慢分块和吞吐量。

### 13.8 分区、保留和清理

- `metric_snapshot` 按 `collected_at` 日分区，保留 `p_future` 作为安全兜底，至少提前创建未来 30 天分区。
- 分区键必须包含在主键和所有唯一键中；分区表不设置 MySQL 不支持的外键。基线主键固定为 `PRIMARY KEY(id, collected_at)`。
- 过期快照在 MySQL 上优先 `DROP PARTITION`，不执行数千万行 DELETE；当表尚未分区时才使用有界分批 DELETE 作为兼容路径。
- snapshot 默认保留 7 天，collection_run 默认保留 30 天，acc 默认保留 90 天；所有保留天数和超时参数都有上下界校验。collection_run 保留期不得小于 snapshot 保留期，清理顺序固定为先删除过期 snapshot 分区，再删除过期 collection_run。
- 普通 DELETE 清理在主采集业务事务提交后单独运行；清理失败记告警，不反向将已成功采集改成失败。
- 分区 CREATE/DROP/REORGANIZE 由独立的 Prefect 维护 deployment 执行，与采集共用同一个 Dashboard 专用账号，但使用独立命名锁，不放在每 5 分钟采集事务内。
- 删除 collection_run 前必须处理所有引用，不得因 current、acc 或历史外键导致清理中断。

### 13.9 读取一致性和历史回放

- 实时查询仅读 `metric_current`，不通过扫描 snapshot 推导当前值。
- 渠道历史按目标时刻对每个 `(node_id, indicator_id)` 取之前最近一条快照；如果超出保留窗口，API 明确返回无数据，不用 current 伪造过去值。
- 查询过去树时按目标时刻读 `hierarchy_parent_history`；查询当前树时读 `hierarchy_node.parent_id`。
- 一个 API 请求需要多次查询时，使用同一个短读事务，避免树和指标分别来自两个提交时刻。

### 13.10 备份、健康检查和可观测性

- 切换前对旧库完成可恢复备份，并实际演练恢复到临时库；只有备份文件不算验收通过。
- `/api/health` 仅表示进程存活；readiness 另外检查 MySQL 连接、期望库名、Alembic head、关键分区、Prefect API 和运行目录磁盘。
- 日志必须包含 batch_no、Prefect flow run id、事务 attempt、结构变化摘要、各阶段耗时和批量写入统计。
- 监控至少覆盖连接池耗尽、命名锁超时、死锁/锁等待、批次超时、分区缺失、磁盘水位、current 覆盖不完和连续采集失败。

## 14. 远端 MySQL 与 Prefect 实施步骤

1. 立即轮换已经公开的 MySQL root 密码，后续不得让应用使用 root。
2. 认证连接远端 MySQL 并执行 `SELECT VERSION()`，要求版本为 MySQL 8.0 以上。
3. 检查远端 `dashboard` 数据库；如果已存在业务表则停止，不自动删除。
4. 创建 `dashboard`，默认字符集使用 `utf8mb4`，节点和指标编码列使用区分大小写排序规则。
5. 创建一个非 root 的 Dashboard 专用账号，迁移、采集、查询和分区维护全部共用；仅对 `dashboard.*` 授予所需 DDL/DML 权限，不授予全局权限或 `GRANT OPTION`。
6. 将 3306 限制为应用服务器来源，并优先使用私网、VPN 或 TLS。
7. 创建独立的 Dashboard V2 Alembic 基线；旧迁移链保留为 legacy，不在新库执行。
8. 按第 12 节的阶段顺序实现新 ORM、结构同步、结构漂移、经理指标解析、目标方案、指标写入和查询服务。
9. 将旧库中的指标启停设置、定制公式和目标值导出并转换到新配置结构；不迁移 current、snapshot、acc 和 collection_run 历史。
10. 执行新库迁移和配置导入，运行指标目录同步。
11. 进入结构初始化模式，建立完整树。
12. 依次运行一次 REALTIME、DAY_ACC 和 MONTH 采集。
13. 在新 Prefect Server 上建立对应 work pool、采集 deployment、分区维护 deployment、schedule 和工作队列，先保持 schedule 暂停。
14. 使用同一 Dashboard 专用账号运行分区维护 deployment，确认未来 30 天分区已建立，并验证采集与分区任务的命名锁不冲突。
15. 验证 Prefect API 健康、Worker 能轮询新 work pool，且新 Prefect 后端使用独立 PostgreSQL，不与 Dashboard MySQL 混用。
16. 切换时同时更新 `DASHBOARD_MYSQL_*` 和 Prefect API 连接配置，重启后端、Worker 及必要的服务进程。
17. 手工触发 REALTIME 并验证后再恢复 schedule，避免新旧 Prefect 同时调度同一 deployment。
18. 观察至少 7 天后再停止旧数据库、旧 Prefect 和 legacy 代码。

## 16. 切换和回滚判定

满足以下全部条件才允许切换：

- V2 树的启用节点、父子关系和请求目标与上游可信响应一致；
- 经理自身指标、渠道指标和所有 current 覆盖校验通过；
- REALTIME、DAY_ACC、MONTH 各至少成功一次；
- V2 API 字段契约、前端主要页面、原有业务能力和四类目标验证通过；
- MySQL 和 Prefect 健康检查通过，并且新旧调度不会重复触发。

出现以下任一情况立即回滚：

- 结构错误停用、多父级、断链或历史归属错误；
- current 大量缺失、旧批次覆盖新批次或稀疏历史无法回放；
- 采集时间超过 5 分钟周期并连续堆积；
- Prefect Worker 连续轮询 500、重复调度或无法保持心跳；
- V2 API 字段契约破坏、原有业务语义变化或前端关键链路不可用。

回滚步骤固定为：

1. 暂停 V2 和旧版全部 schedule，等待在途批次结束或明确标记失败。
2. 恢复旧 MySQL 和旧 Prefect 连接配置，重启后端和 Worker，但仍不恢复 schedule。
3. 使用旧版手工执行 REALTIME，再对当前业务日期执行 DAY_ACC 和 MONTH。
4. 校验旧库树、current、acc、目标和主要 API，确认无在途的 V2 写入。
5. 验证通过后只恢复旧 schedule，保持 V2 schedule 暂停。

旧库在观察期间不得删除。V2 库保留现场用于排查，不将其数据反向合并到旧库。回滚后如需将旧库中新产生的配置再带入 V2，必须重新走配置导出、转换和验证流程。
